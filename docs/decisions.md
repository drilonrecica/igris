## P0-04 — Release tooling

Requirements (SPEC §18): static `CGO_ENABLED=0` binaries for linux/darwin × amd64/arm64, checksums, `make release-local`, never publish automatically, `go install …/cmd/igris@latest` keeps working.

| Option | Pros | Cons |
|---|---|---|
| **GoReleaser** (already installed on the owner's machine) | One declarative `.goreleaser.yaml`; cross-compiles all four targets, archives, `checksums.txt`, `--snapshot` for local dry runs, changelog; can add Homebrew tap/signing later with a few lines | One more dev tool (not a Go dependency, so AGENTS §4 is unaffected); config schema changes between majors |
| Plain release script | No tooling | ~40 lines of bash to re-implement archive naming, checksums, ldflags; more room for platform bugs |

**Recommendation: GoReleaser.**
- Config: `builds` with `CGO_ENABLED=0`, `goos: [linux, darwin]`, `goarch: [amd64, arm64]`, `-s -w` plus `-X main.version={{.Version}}`; `archives` tar.gz with LICENSE/README; `checksum: checksums.txt` (sha256). `release.disable: true` / run with `--skip=publish` so tooling never publishes; the owner creates the GitHub Release and uploads `dist/*` (M7-07).
- `make release-local` = `goreleaser release --snapshot --clean`; run `goreleaser check` as part of it.
- **Signing: no for v0.1.0.** Checksums protect against corruption, and `go install` provides module-proxy/checksum-db verification. Revisit with keyless cosign if/when CI publishes (P0-07).
- **Homebrew tap: later** (post-v1); GoReleaser's `brews` section can be added without changing the pipeline.

SPEC §18 amended accordingly. **Decided 2026-10-06** (owner delegated the call): GoReleaser, checksums only, no signing, Homebrew tap later. Task M7-03 implements it.

## P0-06 — Default task prompt

**Draft, committed for owner review of the wording** (2026-10-06). Files:

- `internal/prompt/rules.md` — the igris rules, written to `.igris/prompts/<ID>.rules.md` and passed with `--append-system-prompt-file` (P0-02/P0-03). Static on purpose: no template variables, so they stay correct even after the first message is compacted away. They state that they override plan/AGENTS/CLAUDE rules (notably "agent updates Status").
- `internal/prompt/task.md.tmpl` — `text/template` with exactly the SPEC §6.1 variables; sent as the first user message via `herdr agent prompt`. Conditional blocks:
  - `Resumed` → inspect `git status`/`git diff` and continue; with `commit = never` it adds that the diff may contain earlier tasks' changes.
  - `CommitPolicy` `never` → don't commit and leave earlier uncommitted changes alone; otherwise "igris commits after verification".
  - `Owner == "agent + user"` → present recommendation/result and wait for explicit decision/sign-off before finishing.
  - `Deps` and `Extra` are listed only when present.

Design choices:
- The non-negotiable parts (one task, no Status edits, no commits, ask-and-wait, `igris done` last, no self-initiated `igris skip`, fix-the-cause on verify feedback) are in the rules *and* briefly restated in the task prompt where they depend on per-run values.
- No template functions are used, so a custom `prompt_template` override needs nothing beyond stock `text/template`.
- Rendered with a scratch program for fresh/resumed × `ask`/`never` × `agent`/`agent + user`: no `<no value>`, no double blank lines. M2-04 turns this into golden tests.

## P0-08 — TUI interaction model

**Approved by owner** (2026-10-06), after the M3-07 smoke run: answering igris by typing `done`, `y` or `retry fresh` works but is not what the owner wants day to day. The TUI should offer every option as something you can click (or tap in Termius) or reach by moving a highlight with the keyboard, like Claude Code's choice prompts and herdr's clickable UI. SPEC §15.3–15.5 and §12 are amended; the M4 rows are reworded to match.

- **Three ways to every action:** a button in a contextual action bar, focus navigation (`tab` between regions, arrows inside, `enter`/`space`), and the existing shortcut key. The bar only shows actions that apply right now.
- **Questions become dialogs:** commit, a session's skip request, session lost, stop and skip open a modal choice list focused on the safe default; options also take `1`…`9`. Destructive choices are never the default, and `esc` only ever picks the non-destructive one.
- **Mouse:** click/tap, wheel scrolling, hover highlight, on by default. `[tui] mouse = false` turns it off, because a TUI that captures the mouse makes the terminal's own text selection need `shift`+drag.
- **No new dependency:** Bubble Tea's mouse messages plus a small hand-rolled hit-region layer (each rendered button, row and option records its rectangle). `bubblezone` would do this but isn't on the P0-01 list and the layer is small.
- **Safety unchanged:** skip-permissions (§7.3) still needs the typed phrase `skip permissions`; no click or key alone can select it. Focus and hover are marked without color, so they work under `NO_COLOR`.
- `--no-tui` keeps the plain stdin commands.
- **Amended** (2026-10-06, M4-01): mouse reporting uses cell motion (presses, wheel, drags), so there is no hover highlight; SPEC §15.4–15.5 updated.
- **Amended** (2026-10-06, M4-07, approved by owner): the visual design pass. Rank colors are set in a new `[tui.rank_colors]` table, with built-in colors for the stock ranks. The default colors are the brand palette (`docs/brand/`). A new `[tui] theme = "auto" | "dark" | "light"` key overrides the background detection, which can fail in a multiplexer or over SSH. Hover stays out, as amended in M4-01. `NO_COLOR` removes color but keeps bold, faint and reverse video. No new dependency: colors go through Lip Gloss, the attributes are plain SGR codes. SPEC §12 and §15.4 updated.
- **Amended** (2026-10-14, HOV-P1, approved by owner): hover is back. Mouse reporting uses all motion (xterm mode 1003, `tea.WithMouseAllMotion`), and the element a left click would act on now is underlined while the pointer is over it: buttons, task and phase rows, HEALTH/RECENT lines, the rows of the phase, doctor and history pages, and dialog options and fields. Never the bar under a dialog or page. Underline is an SGR attribute, not a color, so hover works under `NO_COLOR` and stays apart from focus (reverse video plus `›…‹`). Hover never moves focus. It is drawn over the finished frame by one wrapper around each program's root model (`internal/tui/hover.go`), and each screen only says what is clickable at a point (`hoverAt`, on the hit map the frame recorded). Motion events stop at the wrapper, and a move that keeps the same element under the pointer reuses the last frame, so the stream of motion events costs no redraws. `[tui] mouse = false` turns hover off with the rest of the mouse support, also live from Settings. No new dependency. SPEC §12, §15.4 and §15.5 updated. This supersedes the M4-01 amendment and the "Hover stays out" of M4-07 above.

## V02-P1 — Onboarding scope

**Approved by owner** (2026-10-07), for v0.2. Records the onboarding decisions of the v0.2 plan (2–5) and the details of `doctor`, completions and clipboard copy. SPEC §3.4, §9, §14 and §18 are amended. Tasks V02-01…V02-08, V02-27…V02-29 build on it.

| Option | Pros | Cons |
|---|---|---|
| **`doctor` read-only, prints the fix command** | Safe to run anywhere, any time; one mental model (`check`-like) | The owner types the fix |
| `doctor --fix` | One step | Writes behind the owner's back; a second way to do what `init` and `adapt` already do |

| Option | Pros | Cons |
|---|---|---|
| **Blocker = a `user` task the waiting task depends on** | No plan-format change; igris already notifies on user tasks and waits | A row per blocker |
| New `Blocked by` / `Waits` column or status | Reads naturally | Format change, parser, adapt and docs changes; `blocked` already means "deps unmet" |

| Option | Pros | Cons |
|---|---|---|
| **Hand-written completions + hidden `igris __complete`** | No dependency (cobra stays rejected, P0-01); IDs always match the plan | Three templates to keep in step with the flags |
| cobra's generator | Free scripts | Rewrites the CLI for a feature |

Decided:
- **`igris doctor` is read-only forever.** It never writes and has no `--fix`; every problem comes with the exact command that fixes it. It reports, outside a project, that there is no `igris.toml`, and does not fail for that alone.
- **Check list, in order:** `claude` found + version; `ANTHROPIC_API_KEY`; herdr reachable / inside a pane / integration installed; git repository and dirty tree; `igris.toml` valid, all problems; plan valid, all problems, and drift; `.claude/settings.local.json` has the `igris done` allow rule (as `init` writes it) and warns if any rule allow-lists `igris skip` (SPEC §6.2: skip is deliberately never allow-listed, so a skip always goes through a permission prompt); `.igris/` modes 0700 / 0600; stale or foreign lock; project under `/mnt/` (WSL, points to `docs/check-wsl.md`); notification channels configured — never sent to.
- **Levels** `ok` / `warn` / `fail`; exit 0 unless any `fail` (exit 1); `--json` prints the results.
- **External blockers** (an owner input, a date, a deploy) are a `user` task that names the blocker, with the waiting task depending on it. No plan-format change; `igris adapt` converts prose blockers the same way and says so in `## Adapt notes`.
- **Homebrew:** the tap repository `drilonrecica/homebrew-tap` exists. The formula is generated by `make release-local` from a repo template (`tools/genformula/igris.rb.tmpl`, rendered by a small Go program from `dist/checksums.txt` into `dist/igris.rb`; GoReleaser `brews` is deprecated in 2.x and `goreleaser check` must stay clean). The owner pushes it to `Formula/igris.rb` by hand (`docs/homebrew-tap.md`). Nothing publishes automatically (P0-04 stays true).
- **Column-aware adapt review** and **hiding Task mode on user tasks** are in v0.2.
- **Completions** are hand-written per shell (bash, zsh, fish), embedded as templates, no cobra. A hidden `igris __complete <kind>` supplies phase and task IDs; it reads the plan only (no `.igris/`, no network), prints one candidate per line, and prints nothing and exits 0 on an invalid plan. It is not listed in help.
- **OSC 52 copy** on `y`: new direct dependency `github.com/aymanbagabas/go-osc52/v2` (v2.0.1, MIT), already in the module graph through Lip Gloss, so nothing new is downloaded; it is promoted from indirect to direct and added to the P0-01 approved list. Terminals without OSC 52 ignore the sequence.
- **SPEC amended:** §14 (`doctor`, `history`, `completion`, `init --example`, current run in `status`), §18 (Homebrew), §3.4 and §9 (blocker convention: "a task blocked on something outside the plan depends on a `user` task that names it").

## V02-P2 — Home screen

**Approved by owner** (2026-10-07), for v0.2. The home-screen design (private design note, accepted as written) is transcribed into SPEC §13, §14, §15 (new §15.6), §16 and §17; AGENTS §3 gains `internal/checks`, `internal/report` and `internal/project`. Tasks V02-10…V02-26 build on it.

| Option | Pros | Cons |
|---|---|---|
| **One Bubble Tea program with a screen stack** | One alt-screen session and one background detection (no flicker or misdetection over SSH); home keeps its selection across runs; `tea.Exec` for the editor just works | The run view must be embeddable (a `Leave` hook; Quit becomes **Home**) |
| One program after another, driven from `cmd/igris` | Run view untouched | A driver loop, state lost on every switch, the alt screen re-entered each time |

| Option | Pros | Cons |
|---|---|---|
| **`check` / `phases` / `status` stay working-directory-based** | No silent behaviour change in v0.2 | They differ from `arise` and home, which search upward for the root |
| Search upward like `arise` | One rule everywhere | Changes what an existing command reads without the owner asking |

Decided:
- **Entry.** Bare `igris` opens home only when stdin and stdout are character devices (`ModeCharDevice`), stdin is not `/dev/null`, and `TERM` is not `dumb`; otherwise help to stderr and exit 2, as today. No isatty dependency; the detection is a test seam. `igris arise` with no phase and nothing to resume opens the start-run wizard on a terminal (not with `--no-tui` or `--dry-run`); `igris arise PHASE` and every subcommand are unchanged.
- **One app.** Starting a run from home pushes the existing run view; leaving it (the session keeps running), a confirmed Stop, or a run ending brings the owner back to home with fresh data. At most one engine, only while the run view is on the stack; no background run in v0.2. The adapt review is embedded the same way.

## V03-P1 — Hook-based agent state

**Approved by owner** (2026-10-07), for v0.3. Verified on Claude Code 2.1.293 in a scratch repository, sessions driven through a scratch tmux server; sanitized payloads are in `internal/hook/testdata/`. SPEC §6.3, §7.4, §11, §13 and §14 are amended. Tasks V03-01…V03-03 build on it.

| Option | Pros | Cons |
|---|---|---|
| **Per-session `--settings` file, written by igris, containing only `hooks`** | Nothing persistent; the owner's own sessions never run `igris hook`; nothing for `init`/`doctor` to repair; the hook command names the exact igris binary | igris passes `--settings` itself (still forbidden in `extra_args`) |
| Merge hooks into `.claude/settings.local.json` in `igris init` | Visible, one place | Every Claude session in the project runs the hooks; existing projects need `init` again; the binary path goes stale after an upgrade |

| Option | Pros | Cons |
|---|---|---|
| **On herdr, hook state only fills in when herdr says `unknown`** | herdr's integration (screen-based) stays authoritative where installed; no behavior change for current users | Two sources to reason about |
| Hook state always wins | One source everywhere | Changes working herdr setups for no gain |

Verified behavior:
- A hooks-only file passed with `--settings` merges with the project's settings: the `Bash(…)` allow rules in `.claude/settings.local.json` still apply.
- Hooks run through `/bin/sh -c` with the event JSON on stdin. A failing hook command (exit ≠ 0 and ≠ 2) is non-blocking: Claude Code shows "Failed with non-blocking status code" and carries on. Exit 2 would block a `UserPromptSubmit`, so `igris hook` always exits 0.
- No hook fires while the folder-trust question is shown; `SessionStart` (`source` `startup`, `resume`, `clear`, `compact`) fires once the input box is up.
- `session_id` is the UUID igris passes with `--session-id`.
- Event order for a turn: `UserPromptSubmit` → (`PreToolUse` → `PostToolUse`)… → `Stop`. A permission prompt: `PreToolUse` → `PermissionRequest` → `Notification` (`notification_type` `permission_prompt`, ~6 s later). An `AskUserQuestion` question: `PreToolUse` (`tool_name` `AskUserQuestion`) → `PermissionRequest` → `Notification` `permission_prompt`. After ~60 s idle: `Notification` `idle_prompt`. `/exit`: `SessionEnd` (`reason` `prompt_input_exit`).

Decided:
- **Event → state:** `SessionStart` (startup, resume, clear) → `idle` (`compact` is ignored: it fires mid-turn); `UserPromptSubmit`, `PreToolUse`, `PostToolUse` → `working`; `PreToolUse` for `AskUserQuestion` or `ExitPlanMode`, `PermissionRequest`, `Notification` other than `idle_prompt` → `blocked`; `Notification` `idle_prompt` and `Stop` → `idle`; `SessionEnd` → `exited`. Other events are ignored.
- igris writes `.igris/hooks/<ID>.settings.json` (0600) before each session (fresh, continue and adapt) and adds `--settings <file>` to the argv. The hook command is the absolute path of the running igris plus `hook --root <project root> <Event>`, both paths single-quoted, timeout 5 s.
- `igris hook <event>` (hidden): reads at most 64 KiB of stdin, needs a UUID-shaped `session_id`, takes the project root from `--root` (falling back to walking up from its working directory), writes `.igris/agent-state/<uuid>.json` atomically (`{"state","event","at"}`, 0600, directory 0700), prints nothing, does no network I/O, gives up after 2 s and always exits 0.
- Hook state is untrusted (a session can write the files): read only as a regular file of at most 4 KiB, shape-checked, and keyed by the UUID igris generated. It can at worst raise or clear **Needs you**; only a signal or an owner action advances a task (invariant 3).
- On herdr, herdr's `agent_status` wins; hook state is used only when herdr reports `unknown` (no integration). On tmux, hook state is the state source.

## V03-P2 — tmux behavior

**Approved by owner** (2026-10-07), for v0.3. Verified on tmux 3.7c in a scratch server (`tmux -L … -f /dev/null`); outputs are in `internal/backend/tmux/testdata/`. SPEC §11 is amended. Tasks V03-04…V03-06 build on it.

Verified behavior:
- `new-window -d -P -F '#{window_id} #{pane_id}' -c DIR -n NAME -- prog arg…` prints `@N %N` and execs a multi-argument command **directly, without a shell**: arguments with spaces, `;` and `$HOME` arrive unchanged.
- **`-n` is format-expanded**: `#{pane_id}` expands and `#(cmd)` runs a shell command. `-c` is not expanded. `display-message` text is a format too. So igris escapes every `#` as `##` in window names and toasts (renders as a literal `#`).
- `load-buffer -b NAME -` reads the buffer from stdin (no argv, no expansion); `paste-buffer -p -d -b NAME -t PANE` pastes it with bracketed paste (if the application asked for it, as Claude Code does) and deletes the buffer; `send-keys -t PANE Enter` submits. A multi-line prompt arrives as one prompt.
- `list-panes -t %N -F '#{pane_id}\t#{pane_dead}\t#{pane_dead_status}\t#{pane_current_command}'` describes a pane; a missing one gives `can't find pane: %N` on stderr and exit 1. `display-message -p -t %N` on a missing pane prints an empty line and **exits 0**, so it is not used to detect a gone pane.
- Without `remain-on-exit` a window disappears when its command exits; with `set-option -w -t @N remain-on-exit on` the dead pane stays (`pane_dead` 1, `pane_dead_status` the exit code) until `kill-window`.
- `kill-window -t @N` again → `can't find window: @N`, exit 1. `select-window` on a missing window: same message.
- Outside a reachable server: `error connecting to <socket> (No such file or directory)`, exit 1.
- `tmux -V` prints `tmux 3.7c`; `display-message -p '#{version}'` prints `3.7c`.

Decided:
- The tmux backend needs `$TMUX` (igris runs inside a tmux client) and a reachable server; minimum version **3.2** (older warns via the version table, like herdr; igris never refuses for a version).
- One window per task, named `<ID> · <rank>` (escaped), started detached in the project root with `claude <args…>` as the window command, `remain-on-exit on` set on it right after creation. Window and pane IDs (`@N`, `%N`) are the session ref, shape-checked on attach.
- Prompts go `load-buffer` (stdin) → `paste-buffer -p -d` → `send-keys Enter`; the text is cleaned of control characters except newlines (as for herdr).
- `exited` when the pane is missing or dead, or the hook state says so; otherwise the hook state; `unknown` until the first hook.
- Startup: the session waits for the first hook (`SessionStart`); without one after 15 s (the folder-trust question, or a slow start) it holds the task prompt and reports `blocked`, like herdr's startup handling, and delivers it once the hook state turns `idle`.
- Errors are classified from stderr: `can't find pane`/`can't find window` → session gone.

## V04-P1 — plan format additions

**Approved by owner** (2026-10-08), for v0.4. The v0.4 plan's design, with every open point decided here. Everything is additive: a v0.3 plan and a v0.3 `igris.toml` mean what they meant before (qualified by the amendments below: a plan column that already used one of the new names is read as the new column, a config without `default_mode` runs in `auto`, and an `igris init`-written config lists its notification events explicitly). SPEC §3.2, §5, §6.1–§6.4, §6.7 (new), §10, §12, §13 and §14 are amended. Tasks V04-01…V04-07 build on it.

| Option | Pros | Cons |
|---|---|---|
| **Lint hints only under `check --strict`** | Plain `check` output stays as it is for existing plans; CI opts in | Hints are invisible until asked for |
| Lint hints always shown as `warning:` (the draft plan) | Discoverable | Every existing plan with a long cell or a `yolo` row gets new warnings on every `check` |

| Option | Pros | Cons |
|---|---|---|
| **`before_task` after the task is marked `in progress`, before its session opens** | A failure is the known "in progress, no session" state: retry, done, skip, stop already exist; a crash mid-hook resumes like any other | The plan says `in progress` while only the hook ran |
| Before marking | Plan untouched on failure | A new state with no recovery path; the hook could run twice after a crash with nothing recorded |

| Option | Pros | Cons |
|---|---|---|
| **Resetting the current task pauses the run** | The owner reset it for a reason; nothing relaunches it behind their back | One more `p` to continue |
| Reselect at once | No extra key | The reset task is usually the first ready one again, so it would just restart |

Decided:
- **Columns.** `Verify`, `Timeout` and `Context` become optional canonical columns: matched case-insensitively like the others, aliasable through `[columns]`, task fields instead of `Extra` entries (so they no longer reach the prompt as extra columns). An empty cell, `—` or `-` means "not set" in all three. They are checked only on tasks that are not `done`/`skipped` (like Model, §3.5): igris never runs a finished task, and a finished task's Context may name files that were since moved. On a `user` task each set cell is ignored with a plan warning (`check`, `arise`), like the dependency-like column hint: `M1-02: user tasks have no session, so its Verify (Timeout, Context) is ignored; clear the cell`. `status` shows a VERIFY, TIMEOUT or CONTEXT column only when some task of the plan has that cell set; `status --json` adds `verify`, `timeout` and `context` (an array) per task, omitted when empty.
- **Verify profiles.** `[verify]` maps a profile name to a shell command (`sh -c`, as `run.verify` today), in the owner's config only, never in a plan. Names match `[a-z0-9_-]+`; values must be non-empty. `run.verify` is the profile `default`; setting both `run.verify` and `[verify] default` is a config error, as is a profile named `none`. `run.verify` stays supported (not deprecated). A Verify cell names a profile (case-insensitive) or `none`, which skips verification for that task. Note that in Verify, unlike Model/Mode/Deps, `none` is not "not set": `—` falls back, `none` turns verification off. `[phases.<id>] verify = "<profile>"` (or `none`) is the phase's default; `<id>` matches phase IDs case-insensitively and `verify` is its only key. Resolution per task: the Verify cell → `[phases.<id>] verify` → `default` → no verification. An unknown profile in a cell is a plan validation error (`check`, `arise`, `status`/`phases`, which validate with the config's profile names as they do with `[models]`): `M1-03: unknown verify profile "fsat"; define it under [verify] in igris.toml or use one of: default, fast, none`. An unknown profile under `[phases.<id>]` is a config error; a `[phases.<id>]` naming no phase of the plan is a plan warning (config validation does not see the plan). `verify_timeout` and `verify_max_attempts` apply to every profile. Verify still runs only after the agent's `done` signal and is still skipped when the owner marks the task done. The failure message sent into the session, the run log's `verify_passed`/`verify_failed` detail and the dry run name the profile.
- **Timeout.** A Go duration (`time.ParseDuration`), greater than zero; anything else is a validation error (`M1-03: Timeout "45" is not a duration; write e.g. 45m or 1h30m`). The clock starts when igris sends a session's first prompt: the task prompt for a fresh session, the continue prompt for `retry continue`, and on resume the moment igris reattaches to a live session (elapsed time is not persisted). Every session igris opens or reattaches for the task is one attempt. Once the attempt runs longer than the Timeout, checked while igris watches the session: a `TaskOverdue` UI event, the task card shows **overdue** until the attempt ends, **Needs you** is raised once, the run log gets `task_overdue`, and the `task_overdue` notification goes out once per attempt. igris never closes, stops or kills the session for it. A retry starts a new attempt and a new clock. On a user task Timeout is ignored (above).
- **`task_overdue`** is a new notification event, in the default event list of every channel, urgent like `needs_input` (ntfy priority high, toast sound `request`). `config` accepts it in `events`.
- **Context.** A comma-separated list of repo-relative paths (files or directories), each entry trimmed, surrounding backticks stripped, empty entries and duplicates dropped, `/` as separator, at most 20 entries. Each entry must: not be absolute; have no `..` element; contain no control character (already true of every cell, §3.5); exist; and, with symlinks resolved (`filepath.EvalSymlinks` on the root and on the joined path), stay inside the project root. Violations are plan validation errors in `check` and `arise` (`M1-03: Context "../secrets": paths must stay inside the project; use a repo-relative path`). The root is the project root for `arise` and home, and the working directory for `check`, `phases` and `status` (the directory they read `igris.toml` from). Since every re-read of the plan validates it, a Context path deleted mid-run makes the re-read fail like any other invalid plan. The template variable `.Context` is the list as written (`[]string`); the default task prompt, when it is non-empty, lists the paths as required reading before changing anything. igris never reads or sends the files' contents.
- **Task hooks.** `[hooks] before_task = [argv…]`, `after_task = [argv…]`, `timeout = "2m"` (default 2 m, > 0). An empty or missing list means no hook; a non-empty list needs a non-empty first element, and no element may contain a control character or NUL (config errors). They come from the config snapshot (§13) and run through the command runner as argv, never a shell, in the project root, with igris's environment plus `IGRIS_TASK_ID`, `IGRIS_PHASE`, `IGRIS_RANK` (the alias), `IGRIS_MODEL` (the resolved `--model` value) and, for `after_task` only, `IGRIS_RESULT` (`done` or `skipped`). They run for agent tasks only, never for user tasks or `adapt`, and never in `--dry-run` (which says they would run). `before_task` runs before every session igris opens for the task (fresh, `retry fresh`, `retry continue`), after the task is marked `in progress` and before the pane opens; not when igris reattaches to a live session. On a non-zero exit, a timeout or a hook that can't start: no session is opened, the task stays `in progress`, **Needs you** with the choices of a lost session that has nothing to continue (retry, which runs the hook again; mark done; skip; stop), the run log gets an `error` with the task and a short reason (`before_task hook failed: exit status 1`), and `run_error` is notified. `after_task` runs once after the task is marked `done` or `skipped` (by signal or by the owner) and its session closed; a failure is a warning in the feed, an `error` in the run log and a `run_error` notification, and the run continues. On a failure the last 20 lines of the hook's output (stdout and stderr interleaved), cleaned with `textsafe`, go to the feed only; the run log and notifications get the short reason, never the output.
- **Selection.** `arise --only ID[,ID…]`, `--from ID`, `--until ID`. `--only` cannot be combined with `--from`/`--until`; an empty list or a malformed ID is a usage error (exit 2). The phase range is the positional phase and `--through` as today; with no phase named it is derived from the flags: from the phase of the earliest named task (file order) through the phase of the latest (`--from` alone or `--until` alone: that task's phase). Up front, before anything is written, `arise` exits 1 when a named ID is not in the plan, is outside the phase range, or `--from` comes after `--until` in file order (`arise: --until M3-01 is in phase M3, outside the run's phases M1…M2; widen --through or drop it`). The **slice** is the tasks of the range listed in `--only`, or from `--from` (default: the first) to `--until` (default: the last) in file order. §5.1 runs on the slice: the first slice task `in progress`, else the first unsatisfied slice task whose deps are satisfied. When unsatisfied slice tasks remain but none qualifies, each is reported (UI event and final summary: `not run: M1-05 waits on M1-04 (ready, phase M1)`), never marked, and the run moves to the next phase of the range; this is not a stuck phase (no `phase_stuck`). The run ends when the slice has nothing left to run. `phase_done` is sent only for a phase whose tasks are all satisfied. Tasks outside the slice change only through readiness sync. The interrupted task of an earlier run is still picked up first (§13), also outside the slice, and `arise` says so. `state.json` records the selection with the phases, and a bare `arise` resumes with the same slice; `run_started` names it (`phase M1; only M1-03, M1-05`). The dry run walks the slice.
- **`igris reset ID [--force]`.** Puts a task back to `ready`/`blocked` by readiness (§5.2), finds the project root like `done`/`skip`, and needs a valid plan (else exit 1 listing the problems). `in progress` → reset; `done`/`skipped` need `--force` (else exit 1, `M1-03 is done; pass --force to reset it`); `ready`/`blocked` → `nothing to reset`, exit 0, nothing written. User tasks are reset the same way. With no lock or a stale one: a direct, surgical Status write (§4) plus readiness sync; if `state.json` names the task as the interrupted one, `reset` adds that its session may still be open (close it by hand). With a lock held by a live igris on this host: a signal `.igris/signals/<ID>.json` with action `reset` and `"force": true|false`, replacing any pending signal for that task; the running igris applies it at its next poll (never in the middle of a verify or a commit), re-checking the status: if it is the current task, it closes the session without the idle wait, clears it from `state.json`, rewrites the Status, syncs readiness and turns pause-after-task on, so nothing is selected until the owner continues; any other task gets the Status write and sync. A `reset` signal still pending when the next `arise` starts is applied before selection. A remote lock (another host) → exit 1: run it there, or clear the lock with `arise --force-unlock`. The run log gets `task_reset`. Every path prints what it did (`M1-03: in progress → ready`, or `M1-03: reset sent to the running igris`) and lists dependents that are `in progress`, which are never changed.
- **`check --strict`.** Adds the lint hints below to `check`'s warnings and exits 1 when any **plan or config** warning is reported (lint hints, readiness drift, the dependency-like column, columns ignored on user tasks, an unknown `[phases.<id>]`, deprecated config). Machine warnings (tool versions, `ANTHROPIC_API_KEY`, an `igris.toml` in a parent directory) are still printed but never fail it, so `--strict` works in CI without Claude Code installed. Plain `check` never shows lint hints and its exit codes are unchanged. Lint hints skip `done`/`skipped` tasks; each is `warning: file:line: <message>`:
  - `title`: `M1-03: the Task cell has no **bold** title, so igris shows its first 80 characters; start the cell with **Title**`
  - `long`: `M1-03: the Task cell is N characters (over 400); keep the row short and point to a spec for the details`
  - `owner-step`: an `agent + user` task whose row contains none of `owner`, `approv`, `decid`, `decision` (case-insensitive): `M1-03: agent + user task, but its row never says what the owner does (no "owner", "approve" or "decide"); say what needs the owner's sign-off`
  - `gate`: a task whose ID ends in `-G` (case-insensitive) that does not depend, directly or through other deps, on every other task of its phase: `M1-G: the gate does not depend on M1-04, M1-05 of phase M1; add them to Deps (e.g. M1-01…M1-05)`
  - `yolo`: `M1-03: Mode yolo runs this task with --dangerously-skip-permissions; prefer auto unless it must run unattended`
  - `fable`: a task of rank `fable` in a phase where no other task has rank `opus` or `fable` (the aliases as written): `M1-03: the only heavy-rank task of phase M1 is fable; check that this task needs fable`
  The summary line under `--strict` with warnings is `tasks.md: N warning(s) under --strict; fix them and run igris check --strict again`. `--json` gains `"strict": true` and each lint warning a `"lint": "<name>"` field (names above); `valid` still means the plan validates; the exit code carries the strict result.
- **Status values and writes are unchanged:** `reset` writes only Status cells; no new status value.
- **SPEC amended:** §3.2 (columns), §5.5 (new, selection), §6.1 (`.Context`), §6.2 (`reset` signal), §6.3 (Timeout), §6.4 (profiles), §6.7 (new, task hooks), §10 (`task_overdue`), §12 (`[verify]`, `[phases.<id>]`, `[hooks]`), §13 (`state.json` selection, run log types), §14 (`arise` flags, `reset`, `check --strict`, `status` columns).

**Amended 2026-10-08 after review: resets are requests in their own slot.** Approved by owner, for v0.4.0. A reset signal goes to `.igris/signals/<ID>.reset.json`, separate from the done/skip slot `<ID>.json`, so a session's `igris done`, a verify failure or the end of a task can never replace or delete a pending reset. While igris runs, a reset signal is a request the owner confirms (TUI dialog, `--no-tui` `reset yes|no`), exactly like a session's skip request: sessions can write `.igris/signals/`, so the source can't be trusted. `igris reset` says `reset requested; confirm it in the running igris`. SPEC §5.4, §6.2, §13, §14 and §15.5 amended. **Amended 2026-10-08: `default_mode` is `auto`.** Approved by owner, for v0.4.0. `default_mode` defaults to `auto` (`--permission-mode auto`, verified on Claude Code 2.1.294) instead of `default`; `igris init` and `examples/igris.toml` write it, and `ResolveMode`'s last resort is `auto` too. This is the one exception to "a v0.3 `igris.toml` means what it meant before": a config without `default_mode` now runs sessions in `auto`; `default_mode = "default"` restores every prompt. SPEC §7.1, §7.2 and §12 amended.

| **Quiet hours hold remote channels only; the backend toast is never held** | The toast shows on the machine running igris, not a phone; holding it and toasting a digest later is noise | Toasts still appear at night on a desktop |

Decided:
- **Run log schema v1** (`.igris/runs.jsonl`, SPEC §13). Every line igris v0.5 writes has `"v":1`. Fields (all but `v`, `at`, `type` omitted when empty or zero):
  - `v` (1), `at` (RFC 3339 UTC, as before), `type`, `task`, `rank`, `model`, `detail` (as before, same meaning, so v0.4 readers and `history` keep working).
  - `run`: the run ID, on every line written by a run (`arise`), `run_started` and `run_stopped` included. Format `YYYYMMDD-HHMMSS-xxxx`: the run's start in UTC plus 4 lowercase hex characters from `crypto/rand` (e.g. `20261008-091500-3fa2`), created once when `run_started` is logged; it contains dashes, so it never looks like a `report` index. Lines written outside a run (`igris reset` with no igris running) have no `run`. Readers check the shape `^[0-9]{8}-[0-9]{6}-[0-9a-f]{4}$` and treat a line whose `run` doesn't match as having none.
  - `attempt`: the task's attempt number within this run: 1 for the session of `task_started` or the one reattached by `task_resumed`, +1 for each `task_retried`. On every event of an agent task once it has an attempt (`task_started`, `task_resumed`, `task_retried`, `task_overdue`, `verify_*`, `committed`, `needs_you*`, `task_done`, `task_skipped`). User tasks have none.
  - `session`: the Claude session UUID, on `task_started` (agent tasks: the UUID is generated before the task is marked, `prepareSession`), `task_resumed` (the UUID recorded in `state.json`, if any) and `task_retried` (the new session's UUID; for `retry continue` the same one). Readers shape-check it with `backend.ValidClaudeSession` and treat a bad one as unknown, because `report` prints it into a command.
  - `phase`, `title`, `owner` on `task_started` and `task_resumed`: the task's phase ID, its title (markdown stripped like notification titles, `textsafe.Line`, cut to 80 characters) and owner (`agent`, `user`, `agent + user`).
  - `profile`: the verify profile on `verify_passed`/`verify_failed` (the `detail` keeps its v0.4 text).
  - `commit`: the full commit SHA on `committed` (`git rev-parse HEAD` after the commit; omitted if that fails, with a warning).
  - `duration_ms`: on `task_done`/`task_skipped`, the time from this run's `task_started` or `task_resumed` of the task to the event (wall time by igris's clock: watching, verify, questions, everything); on `verify_*`, the verify command's run time; on `run_stopped`, the run's length.
  - `reason`: on `needs_you`, why igris waits (below).
  - New types: `task_retried` (detail `fresh` or `continue`), `needs_you`, `needs_you_clear`. Everything else is unchanged.
- **Needs you in the log.** `needs_you` is logged every time the engine raises Needs you (the `NeedsYou` UI event) and when a session is lost, with `reason` one of `idle` (settled for `needs_input_after`), `blocked` (waiting for a permission or an answer), `skip_request`, `session_lost`, `task_overdue`, `verify_limit`, `verify_not_sent`, `hook_failed`, `commit` (the commit question under `commit = "ask"`), `reset_request` and `plan_changed` (§5.4); `detail` keeps the few words the notification says. `needs_you_clear` (same `reason`) is logged when that wait ends without the task ending: the agent works again, the owner answers the question, a retry. Readers treat an unknown `reason` as `other`. The config-changed notice (§13) is not a wait (the run goes on) and is not logged as `needs_you`.
- **Compatibility.** A line without `v` is v0 (the v0.2–v0.4 shape, SPEC §13 before this decision); readers accept v0 and v1 lines mixed in one file, ignore unknown types and fields, and read a line with a larger `v` best effort (the known fields), with `history`/`report` adding the note `runs.jsonl has lines from a newer igris (vN); some details may be missing`. Writers never remove or rename a field and never change a field's meaning within v1; adding fields or types is allowed in v1; anything else is v2. Runs are grouped by `run` where lines have it, and by `run_started`…`run_stopped` (or the next `run_started`) pairing for v0 lines, as today.
- **`docs/runlog.md`** (written by V05-01): the file's location, append-only and one JSON object per line; the field table above with types and on which events each appears; every type with its `detail`; the `reason` list; the compatibility rules above; one example line per type; and the v0 shape for reference. SPEC §13 keeps a summary and points to it.
- **`history`** (V05-01) shows the run ID per run when known (text `Run <started> <id> …`, JSON `"run"`), so it can be passed to `report`; otherwise unchanged.
- **`igris report [RUN] [--json]`** (SPEC §14). Finds the project root like `history` (upward), reads `runs.jsonl` with `state.PeekEvents`, read-only, no lock, never creates `.igris/`. `RUN` is a positive integer (1 = the newest run, the default) or a run ID; anything else is a usage error (exit 2). No log or no runs: `no runs recorded yet`, exit 1; an index past the end: `only N runs recorded`, exit 1; an unknown ID: `no run <id> in .igris/runs.jsonl; igris history lists them`, exit 1. A run without a stop is `interrupted`, or `running` while a live igris holds the lock (as `history`). Markdown (stdout, times RFC 3339 UTC, durations like `history`):
  ```
  # igris report · <project>

  Run 20261008-091500-3fa2 · 2026-10-08T09:15:00Z → 2026-10-08T11:02:13Z (1h47m) · completed
  Phases M1, M2 · only M1-03, M1-05

  | Task | Result | Duration | Attempts | Verify | Commit | Needs you |
  |---|---|---|---|---|---|---|
  | M1-03 Config loader | done | 14m02s | 2 | fast ✗ ✓ | 3fa29c1 | 2m10s |
  | M1-05 Docs | skipped | 3m40s | 1 | — | — | — |

  Notes
  - M1-03 done: tests added
  - M1-05 skipped: covered by M1-03

  Resume
  - M1-03: `claude --resume 0f6c…` (run it in the project root)
  ```
  Tasks are grouped by `phase` in log order; tasks with no known phase (v0 lines) go under `## Tasks`. Verify is the profile with one ✗ per failure and ✓ per pass in order; Commit is the first 7 characters of `commit` (the SHA of the task's last `committed`); Attempts counts attempts in this run (v0: `task_started` + `task_resumed` events); every unknown value is `—`. Notes are the `task_done` note or `task_skipped` reason, `textsafe.Line`d, one bullet each, left out when none. Resume lists agent tasks whose last session UUID is known and valid, one `claude --resume <uuid>` each; the section is left out when none. Table cells escape `|`; untrusted text (titles, notes, details) is cleaned with `textsafe.Line`. Run-level errors (the `error` events) follow as `Errors` bullets. `--json` prints one object: `{"run","started_at","ended_at","duration_s","end","phases","selection","done","skipped","unfinished","needs_you_s","commits":[{"task","sha","subject"}],"errors":[…],"tasks":[{"id","phase","title","owner","rank","model","result","duration_s","attempts","verify":[{"profile","passed","duration_s"}],"commit","note","sessions":[uuid…],"resume","needs_you_s"}]}`; unknown strings are omitted, unknown numbers are omitted (never 0 for "unknown"), `resume` is the full command.
- **Needs-you time.** An interval starts at `needs_you` and ends at the first later event of the same run that is `needs_you_clear` with the same task and reason, or for that task `task_retried`, `task_done`, `task_skipped`, `task_reset`, or the run's `run_stopped` (or its last event when it has none). A task's needs-you time is the union of its intervals (overlaps count once); the run's is the union over all its intervals, task-less ones included. User tasks get none: their time is the task's duration. v0 runs have no `needs_you` events: shown `—`, omitted in JSON.
- **TUI progress** (SPEC §15). `n/m · p%` plus a bar, never colour-only: m = the run's tasks of the current phase (all of them, or the slice's tasks in that phase for a sliced run, then labelled `slice`), n = those of them `done` or `skipped` in the plan as last loaded, p = ⌊100·n/m⌋. Wide header: `phase M1 · 7/12 · 58% ██████░░░░` (bar 10 cells, `█` filled, `░` empty); narrow status bar: `M1 · 7/12 · 58%` and a 6-cell bar; with too little width the bar goes first, then the percentage. Hidden when m = 0. Under `NO_COLOR` the bar stays (it is glyphs).
- **Elapsed and ETA.** The card's elapsed time stays what it is (since the task started or was picked up in this run, the 1 s tick). The ETA is the median of the rank's data points: `task_done` durations of agent tasks of the same rank alias, from runs where the task was started in that run (`task_started`, not `task_resumed`, so partial times never count), `duration_ms` when present and the `task_started`→`task_done` timestamps for v0 lines, the most recent 20 per rank, verify and owner waits included (the median absorbs the odd long wait). Skipped tasks and user tasks don't count. Shown only with ≥ 3 data points, always with `≈`, minutes resolution (≥ 1m): `· ≈ 14m left` while elapsed < median, `· over ≈ 18m typical` once past it. No phase ETA. The engine loads the data points once when the run starts (a `report` helper, e.g. `report.RankDurations(events)`) and passes them to the TUI through `tui.Options`; tasks finished during the run are not added.
- **Live tail** (SPEC §11.1, §15). An optional interface, like `PromptHolder`:
  ```go
  type Tailer interface {
      // Tail returns up to n of the last lines the session shows, oldest
      // first, trailing blank lines dropped. A gone session yields an error
      // wrapping ErrSessionGone.
      Tail(ctx context.Context, n int) ([]string, error)
  }
  ```
  herdr: `herdr agent read <name> --source recent-unwrapped --lines n`; when that is empty (or only blank lines, e.g. a dialog on the alternate screen), `--source visible --lines n`. tmux: `tmux capture-pane -p -J -t %N -S -<n>` (joined wrapped lines; the output is the history tail plus the visible screen, so igris drops trailing blank lines and keeps the last n). Both through the command runner with the backend's 10 s timeout; tmux gets a recorded fixture. The fake implements it with scripted lines. The run-view card shows the tail under the state line, before the task text, when `[tui] tail = true` (default) and the current agent session implements `Tailer`: 6 lines in the wide layout, 3 in the narrow one, fewer when the card has no room (the task text then gives way first, ending in `… t: details`). Each line is `textsafe.Line`d, tabs expanded, blank lines dropped, and clipped to the card width by display width. Refreshed every `poll_interval` by a TUI command calling a `Tail func(ctx, n) ([]string, error)` from `tui.Options` (the engine/project side resolves the current session), one call in flight at a time, each bounded by a 2 s context. Any error, an empty result, no session, a lost session, a user task or `tail = false` hides the block silently (no warning, no feed line). The tail is never logged, never in `runs.jsonl`, notifications, `state.json` or `report`; not in `--no-tui`. The conformance suite gains a case that runs only for a `Tailer`: after a prompt, `Tail(ctx, 5)` returns at most 5 lines without error; on a gone session it returns an error wrapping `ErrSessionGone`.
- **Webhook** (SPEC §10, §12). `[notify.webhook] url, secret, events, template`. On when `url` is set and `events` non-empty. `url` and `secret` accept `env:VAR`; the resolved URL must be `http` or `https` with a host (config error otherwise); a `secret` without a `url` is a config error. POST, `Content-Type: application/json`, `User-Agent: igris`, `X-Igris-Event: <event>`; with a secret, `X-Igris-Signature: sha256=<lowercase hex HMAC-SHA256(secret, raw body)>`. Body, every key always present (`""` when unknown): `{"v":1,"event","project","phase","task","title","what","run","at","urgent","text"}`; `at` RFC 3339 UTC; `urgent` is `Event.Urgent()`; `text` is the rendered template or the default text (the message body). A digest (below) has `"event":"digest"`, `X-Igris-Event: digest`, `task`/`title`/`what` empty, `text` the digest text, and adds `"messages":[…]` with one payload object (without `text`/`messages`) per held message. Timeout and retry as every channel (10 s, one retry); errors redacted (the URL and secret are secrets).
- **Slack.** `[notify.slack] webhook_url, events, template`; `webhook_url` accepts `env:` and is a secret (like Discord's). On when set and `events` non-empty. POST `{"text": …}`, default text `*igris · <project>* · <body> (<event>)`. The whole text has `&`, `<`, `>` escaped (`&amp;`, `&lt;`, `&gt;`), so a plan title can't mention `<!channel>` or make links; cut to 4000 characters.
- **Gotify.** `[notify.gotify] server, token, events, template`; `token` accepts `env:` and is a secret. On when `server` and `token` are both set and `events` non-empty; only one of them set is a config error. POST `<server>/message` (`url.JoinPath`), header `X-Gotify-Key: <token>` (never in the URL), JSON `{"title":"igris · <project>","message":<text>,"priority":p}`, text cut to 4000 characters. Priority: 8 for urgent events (`needs_input`, `session_lost`, `task_overdue`), 5 for `verify_failed_limit`, `phase_stuck`, `run_error`, `phase_done` and digests, 3 for `task_done` (and a digest holding only `task_done`).
- **Templates.** `template` on ntfy, Discord, webhook, Slack and Gotify (not the backend toast, whose text stays short). Go `text/template`, no extra functions, `Option("missingkey=error")`, over a struct with exactly `Event`, `Project`, `Phase`, `TaskID`, `Title` (markdown stripped), `What`, `RunID` (strings) and `At` (`time.Time`, local time, so `{{.At.Format "15:04"}}` works); `notify.Message` gains `RunID` and `At` for it. Never file contents or command output. Empty means the channel's default text (today's output, unchanged). It is parsed and executed once against a sample message at config validation, so a bad template or an unknown field is a config error naming the channel (`notify.slack.template: template: …: can't evaluate field Foo; use Event, Project, Phase, TaskID, Title, What, RunID or At`); a template is at most 1000 characters. The rendered text is what the channel sends (ntfy body, Discord `content`, Slack `text` before escaping, Gotify `message`, webhook `text`); titles stay `igris · <project>`. It is cleaned (`textsafe.Clean`: control characters out, newlines kept), trimmed, and cut per channel (ntfy 4096 bytes, Discord 2000 characters, Slack, Gotify and webhook 4000); an empty result at run time falls back to the default text.
- **Quiet hours.** `[notify] quiet = "HH:MM-HH:MM"` (24 h, local time; `""` = off, the default); start = end is a config error; the window is `[start, end)` and crosses midnight when start > end; it is evaluated on the wall clock each time, so DST shifts move it with the clock. `[notify] break_through` lists events never held (default `["needs_input", "session_lost", "task_overdue"]`; `[]` holds everything; names validated like `events`; written out by `config.Write` only when it differs from the default, like `events`). Inside the window a message for ntfy, Discord, webhook, Slack or Gotify whose event is not in `break_through` is held per channel (after that channel's `events` filter) instead of sent; the backend toast is never held. The router takes an injectable clock (`Now`) and gets `Flush(ctx)`: the engine calls it from its poll loop and from every other place it waits on the clock (questions included), at most once per `poll_interval`; when the clock is outside the window and a channel holds messages, that channel gets one digest. Held messages are also flushed as a digest at run stop (igris can't hold them after it exits). Digest text: `quiet hours 22:00–07:00: N held` then one line per held message, `HH:MM <event>: <default body>` (local time), at most 20 lines, then `… and K more`; templates are not applied to digests; Discord/Slack frame it like a message (`**igris · <project>**` / `*…*`). The run log gets `notification` events `<event> held for <channel> (quiet hours)` and `digest of N via <channel>`. `notify test` bypasses quiet hours and `task_done_digest`.
- **`task_done_digest`.** `[notify] task_done_digest = 0` (default: one message per task), an integer N ≥ 2, or `"phase"`; 1 means 0; anything else is a config error. With N: `task_done` messages are collected per channel and sent as one `task_done` message when N are collected, when the phase ends (before its `phase_done`/`phase_stuck`, or when the run moves to the next phase) and at run stop. With `"phase"`: at phase end and run stop only. The grouped message is a `task_done` `Message` with empty `TaskID`/`Title` and `What` `3 tasks done: M1-01, M1-02, M1-03` (IDs cut after 10 with `…`), so templates apply; during quiet hours it is then held like any `task_done`.
- **Config** (SPEC §12). `Secrets` gains `WebhookURL`, `WebhookSecret`, `SlackWebhook`, `GotifyToken`, all resolved by `Resolve` and scrubbed from router errors. `[notify]` gains `quiet`, `break_through`, `task_done_digest` (a `toml.Unmarshaler` type accepting an integer or `"phase"`). `[tui]` gains `tail` (default true). `igris init` writes none of the new channel blocks; `doctor` lists the new channels in its notification check (never sending); `notify test` covers them.

**Amended 2026-10-08 after review: notification hardening.** For v0.5.0, before its release. SPEC §10, §12, §14 and §16 amended.
- **No redirects.** Every channel's HTTP client returns the redirect response instead of following it (`CheckRedirect` → `http.ErrUseLastResponse`, also on a client passed in): following would carry `X-Gotify-Key`, `X-Igris-Signature` or a secret URL (as `Referer`) to whatever host the `Location` names, and a `200` there counted as delivered. Any `3xx` is a failure, `server answered 307 (redirect); set the final URL in igris.toml`; the `Location` is never shown.
- **Fixed error texts.** A transport failure is one of `can't resolve host`, `connection refused`, `TLS failed`, `timed out`, `cancelled`, `connection failed`; a status is `server answered <code> <Go's status text>` (not the server's reason phrase); a URL that doesn't parse is `<key> is not a valid URL …`. net/http's error text (URL, host, `url.Parse` quoting parts of the URL) never reaches a result, so the router's redaction is the safety net only.
- **Redaction order.** `Redact` replaces the longest secret form first (escaped forms included), through a marker, so a secret that contains another never shows in part and `[redacted]` is never searched again.
- **Discord and Slack URLs** must be `https` with a host: a literal one is a config error at load, an `env:` one an error from `Resolve`; the text names the key, never the value. Gotify, ntfy and the webhook keep `http` (a LAN server); `Warnings` (shown by `check`, `arise`, `doctor`) flags `http://` for ntfy with a token, Gotify (the token goes in the clear) and a literal webhook `url`.
- **Templates can't loop.** A parsed template whose tree has `range` or `template` (anywhere, inside `if`/`with` too) or that defines templates (`define`, `block`) is a config error naming the channel: `notify.<channel>.template uses {{range}}; a notification template may use only variables, if/else and with`. A message has no lists, and a loop could spin the CPU on every message; the 64 KiB output cap stays for what is left (`printf` widths).
- **Output limits.** ntfy's default body is cut to 4096 bytes like a template's. A webhook digest lists at most 50 held messages (the oldest) in `messages` and adds `truncated`, the number left out (`0` when none); only digests have the two keys.
- **Discord masked links.** Discord content, the default and a template's, has `\`, `[` and `]` escaped with a backslash, so a plan title can't make `[text](url)` show one address and open another; mentions stay off through `allowed_mentions`.
- **Config hash.** `[tui] tail` is in the hash only while `false` (`TUI.MarshalJSON`), as the hash keeps `tui.mouse` and `tui.theme` and the v0.5 `[notify]` keys follow the same omit-while-default rule. So every v0.4 config keeps its hash (the defaults' hash is pinned to v0.4.0's in a test), and a run interrupted under v0.4 resumes without the config-changed notice; the CHANGELOG's Migration item about it is gone.
- **`task_done_digest` errors.** A value that is no digest (a negative or too large number, another word, a float, a list) decodes to an invalid marker instead of failing the TOML decode, and `Validate` reports `notify.task_done_digest is invalid; use 0 …, a number of tasks of at least 2, or "phase"` together with the file's other problems.
- **Stopping.** `Router.FlushAll` (the run's end) makes one attempt per message, no retry, under an overall 15 s deadline (`finalFlushTimeout`). `igris arise` stops catching SIGINT/SIGTERM once the first one arrives (`signal.Stop` before its context ends), so a second one exits at once instead of being ignored while the flush runs.
- **`notify test --event`.** With channels set up but none sending the event, it says `no channel sends <event>; add it to a channel's events in igris.toml`; with no channel at all the hint says "the backend toast", not "the herdr toast".

**Amended 2026-10-08 after review: needs-you time and reading the run log.** Approved by owner (Decision W), for v0.5.0, before its release. SPEC §13 and §14 and `docs/runlog.md` amended.
- **Needs-you time is the time igris waited on the owner** (Decision W). An `idle` or `blocked` wait also ends at the session's done signal (cleared before its verify runs; a verify failure and a new idle stretch is a new wait), so verify time and the agent's work on a failure never count. `task_overdue`, `verify_limit` and `verify_not_sent` are cleared (`needs_you_clear`) when the agent is seen `working` again: an overdue task that keeps working waits on nobody. A `plan_changed` wait starts when the run holds, which is between tasks, after the current task ended; it ends when the owner resumes.
- **One wait per task and reason.** A wait already open for the task and reason is not logged again (a second skip request, the verify limit hit again, another plan edit while the run holds); the notification and the UI still say it again. Readers end every open wait of the task and reason at a `needs_you_clear`, so logs written before this rule, with a wait logged twice and cleared once, add up.
- **Attempts count per task per run.** A task reset and started again in the same run gets the next attempt number, not 1 again.
- **One bad line never hides the history.** `history`, `report`, the home screen and the ETA read the log with `state.PeekLog`, which skips every line it can't read (not JSON, not an event, a v0/v1 field of the wrong type, longer than 1 MiB) and counts it; `history` and `report` add `N unreadable lines in runs.jsonl skipped` (joined to the newer-version note with `; `). A cut-off last line without a newline is skipped without being counted (igris may be writing it). A line with a larger `v` whose fields changed type keeps the fields that decode. `Append` writes a newline first when the file doesn't end in one, so a crash-cut line never swallows the next event. The engine's own `Dir.Events` (tests) stays strict.
- **Values a run can't have are unknown.** `duration_ms` below 0 or over 30 days reads as unknown, so sums can't overflow. A known duration under a second is shown as 1s (task, verify, run, needs-you; `duration_s` in JSON too), never as unknown. `"phases"` is `[]`, never `null`, and history's text leaves out `phase` for a run without its `run_started` line.
- **Report.** `RUN` is any positive integer (one too large for an int is past the end: exit 1 `only N runs recorded`). The Commit cell is the task's last commit, `—` when that commit's SHA is unknown. Resume names the latest session only: when the task's latest session line has no valid UUID, it is left out rather than pointing at an older conversation. The markdown escapes `\` `` ` `` `*` `_` `[` `]` `(` `)` `!` `<` `>` `#` `|` in text from the log (titles, notes, IDs, phases, errors, the run's end), so a title can't make a link, image, emphasis or HTML; `--json` keeps the cleaned text.

Users can check that a download is the one the owner released, each release lists what it is built from, and CI watches for known vulnerabilities and for builds that don't reproduce. P0-04 left signing for later ("revisit with keyless cosign if/when CI publishes"); P0-07 keeps CI from publishing. Both hold: nothing here publishes from CI.

| Option | Pros | Cons |
|---|---|---|
| **SSH signatures** (`ssh-keygen -Y sign`) | No new tool for the owner or for users (OpenSSH ≥ 8.1 on every Linux and macOS); the same key signs git tags, which GitHub shows as Verified; signing stays local | Users need an `allowed_signers` line (published in the repo); less known than minisign |
| minisign, local | Small, made for this, short public key | A new tool for the owner and every user who verifies |
| cosign keyless, local | No key to keep: a browser login signs, the transparency log records it | Puts the owner's email in a public log for good; users need cosign; a browser login per release |
| cosign keyless in CI | Provenance and signing in one workflow, no key on the owner's machine | Reverses P0-07: CI gets write rights and publishes |

**Decisions:**
- **Signing: SSH signatures.** `checksums.txt` is signed with `ssh-keygen -Y sign -n file`, which writes `checksums.txt.sig`. Each archive is covered through its line in `checksums.txt`. The key is a dedicated Ed25519 release key (`~/.ssh/igris-release`), not the owner's GitHub login key. Verifying is `ssh-keygen -Y verify -f allowed_signers -I igris -n file -s checksums.txt.sig < checksums.txt`, then `sha256sum -c --ignore-missing checksums.txt` (`shasum -a 256 -c --ignore-missing checksums.txt` on macOS). The commands were tried on a throwaway key: a good signature verifies, and a changed `checksums.txt` fails.
- **The owner signs every release.** The key has a passphrase the agent never sees. At release time the agent prepares the release commit, then stops. The owner runs `make sign VERSION=X.Y.Z`: it creates the annotated tag signed with the same key (`gpg.format=ssh`), builds the release from that tag, and signs `dist/checksums.txt`. The agent then checks the tag and the signature against `allowed_signers` before `gh release create`. A compromised agent session can build, but it can't sign.
- **The public key** is published in three places: `allowed_signers` at the repository root (`igris namespaces="file,git" ssh-ed25519 …`), the README's verifying section, and the owner's GitHub SSH signing keys (for Verified tags).
- **Rotation.** A new key is added to `allowed_signers` and announced in the CHANGELOG and README. The old line stays with `valid-before="YYYYMMDD"`, so older releases still verify.
- **SBOM: syft through GoReleaser's `sboms`** (`artifacts: archive`), one SPDX JSON per archive, listed in `checksums.txt` so the signature covers it. syft is a release-time tool on the owner's machine, not a Go dependency; this approves it. A `go version -m` manifest was the no-tool alternative, but it isn't a format scanners read.
- **CI**, still `contents: read`, no secrets, never publishing:
  - **govulncheck** on push and pull requests, pinned (`go run golang.org/x/vuln/cmd/govulncheck@vX.Y.Z`); a reachable vulnerability fails the job.
  - **govulncheck weekly** (`schedule`), so an advisory against unchanged code shows up between pushes.
  - **Reproducible build:** the job builds the same commit twice with the release flags (`CGO_ENABLED=0`, `-trimpath`, the release ldflags, the commit's timestamp) and fails if the binaries differ.
  - **Fuzzing** (V06-05): a short run per fuzz target on push, with the corpus committed.
- **Unchanged:** releases before v0.6.0 stay unsigned (checksums only). Homebrew pins each archive's sha256 from `checksums.txt` and doesn't check the signature, which is for direct downloads. `go install` keeps the module proxy and checksum database.

SPEC §18 amended. Tasks V06-01 (signing, `make sign`, `allowed_signers`, README), V06-02 (SBOM, govulncheck, reproducible build) and V06-05 (fuzzing) implement it.

## WAIT-P1 — Waiting on background work, and one reminder

**Approved by owner** (2026-10-14), after Needs you kept firing on a task whose agent waited for iOS simulator and Android emulator tests. Two cases raised Needs you with nobody needed yet: an agent that ends its turn while background work runs (Claude Code resumes it when the work is done), and an agent that says it is finished but never runs `igris done`.

- **Claude Code says what is pending.** Its `Stop` hook input carries `background_tasks` (shell, monitor, subagent, workflow, … with `status`) and `session_crons` (`ScheduleWakeup`, `CronCreate`, `/loop`). Recorded with Claude Code 2.1.299 (`internal/hook/testdata/stop_*.json`):
  - a `Stop` while a background shell runs lists it with `"status": "running"`;
  - the finished shell re-invokes the session through `UserPromptSubmit`, and the next `Stop` has an empty list;
  - a scheduled wakeup shows in `session_crons`;
  - `idle_prompt` still arrived about a minute after the `Stop`, while the shell ran.
- **A new agent state `waiting`.** `igris hook` records it for a `Stop` with a background task that isn't finished, or with any cron. It reads only statuses and counts, never commands or descriptions, and it reads leniently, so an unexpected shape never loses the `Stop`. An `idle_prompt` doesn't replace `waiting`. With herdr, a hook `waiting` beats herdr's `idle`/`done` (herdr sees only a finished turn); herdr's `working` and `blocked` still win.
- **The engine.** `waiting` is not idle. It clears an idle or blocked Needs you and shows `waiting on background work (4m)`. Past `waiting_limit` (new key, default `30m`, owner's choice; a task's `Timeout` applies as before) it raises Needs you with the new run-log reason `waiting`, once per stretch. Adapt follows the same rule. A forged `waiting` (sessions can write `.igris/`) can at worst delay Needs you by `waiting_limit`, in line with the existing rule that a forged state can raise or clear it.
- **One reminder** (owner's choice). An agent task idle or `done` for `needs_input_after` without a signal is first sent one fixed prompt: run `igris done <ID>` if finished, otherwise say in one line what it waits for. Then `needs_input_after` counts again, and Needs you follows as before. It happens at most once per attempt, so there is no loop with an agent that keeps answering "waiting for the owner". Never when the agent is blocked (a permission or a question), never for adapt, and `nudge = false` turns it off. A reminder that can't be sent raises Needs you at once. It shows in the feed, not in the run log, like the v0.5.1 Enter.
- **Config hash.** Both keys are optional and left out of the hash while unset, so a v0.5 config keeps its hash and an interrupted run resumes without the config notice.

SPEC §6.3, §11.1, §12, §13 and §15 amended. Task WAIT-01 implements it.

## V06-P2 — Worktree mode

**Approved by owner** (2026-10-14, "go with your recommendations"), for V06-03. A run can work in a git worktree on a branch of its own (`[run] worktree = true` or `arise --worktree`), so an unattended run (`auto`, skip permissions) leaves the owner's checkout alone and its result is a branch to review. It is one worktree per run and one task at a time; v2's parallel runs (a worktree per task) build on it.

- **The plan stays in the project root.** igris reads and writes Status there, as in any run; the worktree's copy is never updated, and the task prompt names the project's plan by its absolute path. `igris status`, home, resume and plans git ignores keep working, and one plan written by igris alone is what many worktrees need in v2. The branch's commits hold the sessions' work only. Rejected: the worktree's copy, which puts Status in the branch's commits but needs a fallback for untracked plans and leaves `igris status` in the checkout stale until a merge.
- **igris never merges.** A completed run whose worktree has nothing uncommitted removes it (`git worktree remove`) and keeps the branch, printing the merge command. A dirty worktree, a stopped or stuck run keep it; the next `arise` continues there.
- **Opt-in, no warning** (ROADMAP open question #7). The skip-permissions confirmation of `igris arise` suggests `--worktree`; the README recommends it for unattended runs.
- **What it took** (found in real runs with Claude Code 2.1.299):
  - `igris done` from inside the worktree found the worktree's tracked `igris.toml` as the root, so `state.FindRoot` returns the project for any path under `.igris/worktrees/<name>`.
  - The worktree lacks `.claude/settings.local.json` (untracked), so the `igris done` allow rules go into the session's `--settings` file, with `Read(//<plan path>)`: the plan is outside the worktree, and reading it asked for approval. That file held hooks only until now (SPEC §7.4); these rules are the only addition, and only in worktree mode.
  - **Amended** (2026-10-14, after a security review of the commit flagged it as a widening): the session gets only the `igris done` rules the project's `.claude/settings.local.json` already has, so worktree mode never allows what the owner's own settings don't. The plan rule is left out when the plan's path holds pattern characters, which Claude Code would read as a pattern matching more than the plan.
  - Claude Code didn't ask to trust the worktree once the project was trusted.
  - The start-up git warning ("igris's first commit includes them") is wrong for a worktree: it is reworded for a new one and left out when a run continues in its worktree, whose project now always has the plan's Status edits.

SPEC §6, §6.2, §6.7, new §6.8, §7.3, §7.4, §12, §13 and §14 amended. Task V06-03 implements it.

## V06-P3 — What the commands igris runs see of its environment

**Approved by owner** (2026-10-14, with the V06-04 plan). Verify commands, task hooks and the git hooks a commit triggers are the project's code, which a session writes. They ran with igris's whole environment, including the variables `igris.toml`'s `env:` references read notification secrets from. A session that can't read the token can write a test that prints it into verify's output, which igris pastes back into the session.

- **Secrets' variables are never passed**, to verify, task hooks or git, with or without an allowlist. They come from the config snapshot's `env:` references (`config.SecretEnvNames`, the same field table `Resolve` reads). Listing one in `run.env` is a config error rather than a silent drop.
- **`[run] env` is an opt-in allowlist** for verify and task hooks (ROADMAP v0.6): names, or prefixes ending in `*` (`LC_*`). Unset keeps today's behavior (the whole environment, minus the secrets). `PATH` and `HOME` always pass: `sh` and nearly every tool need them, and leaving them out is a footgun with no security value. `env = []` is an error: a written config drops an empty list, which would turn "nothing" into "everything".
- **Git gets the stripping, not the allowlist**: commit hooks and signing need `SSH_AUTH_SOCK`, `GPG_TTY` and others no list would think of.
- **Out of scope:** the Claude sessions' environment (it comes from the backend's server, not from igris), `adapt` and the owner's editor (no project code runs).
- Checked in a real run: without `env`, verify saw everything but `IGRIS_TEST_TOKEN` (the ntfy token's variable); with `env = ["LANG"]`, it saw `HOME LANG PATH` and what `sh` sets itself (`PWD SHLVL _`).

SPEC §6.4, §6.5, §6.7, §12 and §16 amended. Task V06-04 implements it.

## V07-P1 — The 1.0 contract

**Approved by owner** (2026-10-14), decided together for v0.7. 1.0 is meant to be a tool other people build a workflow on: scripts read its `--json`, CI runs `igris check`, other tools write plans igris reads, webhooks feed dashboards. This decision fixes what 1.x promises not to break, cleans up the few shapes that are awkward to promise forever while igris is still 0.x, and sets how versioned files evolve. The inventory behind it was taken from v0.6.0.

**Frozen for 1.x** (owner chose the ROADMAP's list plus the task-hook environment and the webhook headers):
- **The plan format** (format 1): SPEC §3–4, written out on its own in `docs/plan-format.md` (V07-01). It covers columns, status values, deps grammar with ranges, phase ID rules and the writer's guarantees (only Status cells change, bytes, BOM and CRLF preserved).
- **`igris.toml`**: keys, defaults and validation. Unknown keys stay an error.
- **CLI**: commands, flags, arguments and exit codes (SPEC §14). Text output is for people and is not frozen; `--json` is the machine interface.
- **`--json` output** of `check`, `phases`, `status`, `history`, `report` and `doctor`, each with a JSON schema in `docs/json/` (V07-03).
- **Signals and the session contract**: `igris done`, `skip` and `reset` with their flags and exit codes, and the signal file format.
- **`.igris/`**: the paths in SPEC §13, `state.json` (versioned, below) and the run log (`runs.jsonl`, `"v": 1`, `docs/runlog.md`).
- **Template variables** of `prompt_template`, `commit_message` and the notification `template`s.
- **The generic webhook**: its JSON payload (`"v": 1`), the `X-Igris-Event` and `X-Igris-Signature` headers and the HMAC-SHA256 signature.
- **The task-hook environment**: `IGRIS_TASK_ID`, `IGRIS_PHASE`, `IGRIS_RANK`, `IGRIS_MODEL`, and `IGRIS_RESULT` for `after_task`.

**Not frozen:** the TUI (layout, keys, colors); the default task prompt's wording; text output; the hidden `hook` and `__complete` commands; the contents of `.igris/agent-state/`, `.igris/hooks/`, `.igris/prompts/` and `igris.lock`; the text igris sends to ntfy, Discord, Slack, Gotify and the backend's toasts; the Go packages (`internal/` stays internal; igris is not a library).

**What "frozen" allows in 1.x.** Additions: new optional plan columns (an older igris passes them to the prompt as extra columns), new config keys with defaults, new commands and flags, new JSON fields, new run-log event types, new template variables. Not allowed: removals and changed meanings. Readers of JSON, the run log and the webhook ignore fields and event types they don't know. Something deprecated in 1.x warns until 2.0 and is only removed then.

**JSON cleanup before the freeze** (owner chose to clean up now; breaking, so listed in the CHANGELOG):
- Every `--json` output is an object with `"v": 1`. `doctor` becomes `{"v": 1, "checks": [...]}` instead of a bare array.
- An empty rank or mode is left out instead of `"—"`.
- The `counts` key `"in progress"` becomes `"in_progress"`. Status values in a task's `status` field are unchanged: they are the plan's words.
- `run.signals` becomes a list of `{"task": "M1-03", "action": "done"}` objects instead of `"M1-03 done"` strings.
- The invalid-plan output of `phases` and `status` and the per-task view of `history` keep their own shapes, each with its own schema.
- `doctor`'s `confirm`, `file`, `line`, `task`, `from` and `to` fields are documented and get a golden test.

**Exit codes: 0, 1, 2** (owner's choice). 0 is success, 2 is a usage error, 1 is everything else. SPEC §14 gets a table listing, per command, what exits 1. 3–9 are reserved: 1.x may give a case that exits 1 today its own code from that range. Scripts test for non-zero, or for 2, and never for exactly 1.

**`state.json`: keep the key, write 3, migrate** (owner's choice). The key stays `"version"`; the ROADMAP's `"v"` would be a rename for nothing. 1.0 writes version 3, and the selection is an optional field in it. It reads 1, 2 and 3 and migrates 1 and 2 in memory; the next save writes 3. A newer version is refused with "written by a newer igris (version N); upgrade igris, or delete the file to start a new run". A file that is damaged (bad JSON, a value of the wrong shape) is reported as damaged, separately from an old one. In 1.x a new field gets a new version only when an igris that ignored it would do something wrong, as the selection did and the worktree should have. Every 1.x igris reads every older version.
- **The config hash is part of the contract.** A config that doesn't set a key added later keeps its hash, so an interrupted run resumes without the "config changed" notice. Today `omitempty` fields and `TUI.MarshalJSON` do this; SPEC §13 now says so.

**Plan format marker: optional forever** (ROADMAP open question #8). A plan may declare `<!-- igris:format 1 -->` on a line of its own before the first phase heading; without one it is format 1. A plan marked with a format igris doesn't know is refused with "plan format N needs a newer igris". A format 2, if one ever comes, needs its marker, so no plan written today ever has to be edited.

**Leniency is documented, not removed** (owner's choice). What the parser accepts today becomes part of format 1: Mode and Verify values in any case (`YOLO`, `Fast`), phase IDs compared case-insensitively for duplicates and `[phases.<id>]`, tabs trimmed from header cells along with `*` and backticks. Model ranks stay case-sensitive, with the "did you mean" hint. No plan that loads in v0.6 stops loading.

**Deprecation removed: `claude.command`.** It was deprecated in v0.1.2 with a promise to remove it in v0.2, which slipped; the CHANGELOG says so. `igris config migrate` (V07-05) deletes it. After V07-06, a config that still has it fails as an unknown key, and the error names `igris config migrate`. Nothing else is deprecated.

SPEC new §19 (Compatibility) added. Tasks V07-01 (plan format, marker, leniency), V07-02 (state version 3, migration, damaged vs old, config hash), V07-03 (JSON cleanup and schemas), V07-04 (exit codes, help audit), V07-05 (`config migrate`) and V07-06 (remove `claude.command`) implement it.

**Amended** (2026-10-14, V07-04, the owner left it to the agent): **`arise --dry-run` on a stuck phase exits 0.** A preview that shows a phase as stuck did what it was asked; a real run of that phase exits 1. CI that wants to catch a stuck phase reads `igris status --json` (`"outcome": "stuck"`). SPEC §14 says so, and a test pins it.

**Amended** (2026-10-20, V10-05, approved by owner): **config validation tightened before 1.0.** The final security review found that some configs rc.1 accepted let a session's permissions, tools, directory or system prompt be changed from `igris.toml`, or put hidden text on the terminal. Validation is part of the frozen `igris.toml` surface, so this reopens the decision; it is allowed because 1.0.0 is not out yet, and from 1.0.0 on these rules are frozen like the rest. Configs that rc.1 accepted and 1.0 rejects:
- `claude.extra_args` with `--allowedTools`/`--allowed-tools`, `--disallowedTools`/`--disallowed-tools`, `--tools`, `--add-dir`, `--permission-prompt-tool`, `--bare`, `--setting-sources`, `--plugin-dir`, `--plugin-url`, `--mcp-config`, `--strict-mcp-config`, `--agent`, `--agents`, `--system-prompt`, `--system-prompt-snapshot`, `--ide`, `--worktree` (and `-w`, alone or clustered), `--fork-session` or `--no-session-persistence`;
- a control character in any `claude.extra_args` value, or in a `[models]` rank or model;
- `notify.ntfy.server` or `notify.gotify.server` with a `user:password@` part (use `token`);
- an `igris.toml` that isn't a regular file or is over 1 MiB (a plan over 16 MiB, likewise).

Also new, and additive under the rules above: `state.json` records `config_changed` within version 3 (an igris that ignores it behaves as rc.1 did, so no version change), the run log gets a `config_changed` event, and `arise` asks before using an `igris.toml` that changed during the previous run (declining exits 1, like any start-up confirmation; stdin ending counts as declining). The CHANGELOG lists the rejected configs under **Changed**.

## V11-P1 — Plan approval from igris

**Approved by owner** (2026-10-20), for v1.1; the owner chose the mode syntax, `then`, `approve_timeout` and `plan:yolo` handling, and left the rest (no approval from igris in `--no-tui`, the plan in the commit body, the forged-decision risk, what V11-02 verifies) to the agent. Verified on Claude Code 2.1.304 in a scratch repository, with sessions driven through a scratch tmux server (sonnet), both with the owner's plugins and with `--setting-sources project,local` (no user hooks). Sanitized payloads: `internal/hook/testdata/pretooluse_exitplanmode.json` and `permissionrequest_exitplanmode.json`. SPEC §6.3, §6.5, §7.1, §7.3, §12, §13, §15.6 and §19 are amended now; V11-02 adds the new Mode values to §3.2, `docs/plan-format.md` and the adapt prompt's copy of §3 (`internal/prompt/format.md`) together with their validation, so neither `adapt` nor the format doc names a value igris doesn't accept yet. Tasks V11-01 (hook, TUI view, plan storage) and V11-02 (mode after approval) build on it.

Verified behavior:
- **Payload.** A plan presented for approval fires `PreToolUse` and then `PermissionRequest` with `tool_name` `ExitPlanMode`, `permission_mode` `plan`, and `tool_input` `{"plan": "<the plan, markdown>", "planFilePath": "~/.claude/plans/<slug>.md"}`. `PermissionRequest` has no `permission_suggestions` and no `tool_use_id`. Before the call, Claude writes the plan to `planFilePath` with `Write` (a `PreToolUse`/`PostToolUse` pair for `Write`, allowed in plan mode).
- **Deny with feedback.** `{"hookSpecificOutput":{"hookEventName":"PermissionRequest","decision":{"behavior":"deny","message":"…"}}}` closes the dialog. Claude gets the message, revises, and calls `ExitPlanMode` again: a new `PermissionRequest` with the new plan. The transcript records `hook_permission_decision` `deny`.
- **Allow needs `updatedInput`.** A bare `{"behavior":"allow"}` is parsed and logged ("returned permissionDecision: allow") but **ignored for `ExitPlanMode`**: the dialog stays. `{"behavior":"allow","updatedInput":<the tool_input received>}` approves: the pane shows "Allowed by PermissionRequest hook" and the session implements the plan.
- **`setMode`.** `updatedPermissions: [{"type":"setMode","mode":"acceptEdits","destination":"session"}]` alongside the allow leaves plan mode in accept-edits (status line `accept edits on`); `"mode":"auto"` leaves it in auto mode (`auto mode on`, an unfamiliar `date > when.txt` then ran unprompted). `bypassPermissions` was **not** verified (the probe was refused by the auto-mode classifier of the session running it) and neither was `default`; V11-02 verifies both.
- **While the hook waits** the pane shows Claude Code's own plan dialog at once ("Ready to code? … Would you like to proceed?"); the hook and the dialog run side by side. `Notification` `permission_prompt` ("Claude Code needs your approval for the plan") follows ~6 s after `PermissionRequest`. The first answer wins: answering in the pane cancels the waiting hook at once (debug log: "Hook PermissionRequest:ExitPlanMode (PermissionRequest) cancelled"), and the hook's decision closes the dialog.
- **Hook timeout.** At the entry's `timeout` Claude Code kills the hook ("timed out after 15000ms", "cancelled"); the dialog stays and the owner answers in the pane. No error reaches the session.
- Other plugins' `PermissionRequest` hooks run in parallel and don't block the decision; plain-text output from them is ignored.

Decided:
- **The one exception to the 2 s deadline.** For a session whose mode is `plan` or `plan:<mode>`, the settings file (§6.3) gets a second `PermissionRequest` entry with `"matcher": "ExitPlanMode"` that runs `'<igris>' hook --root '<root>' plan-approve`, with a Claude Code `timeout` of `approve_timeout` + 30 s. The state hooks are unchanged (still 5 s, still 2 s inside igris). Only `plan-approve` waits: it reads at most 1 MiB of stdin (a plan can be long), needs the UUID-shaped `session_id` and `tool_name` `ExitPlanMode`, writes a request, and polls every 200 ms for igris's decision. It exits with **no output** (so the pane decides) when `approve_timeout` passes, when `igris.lock` is gone or its PID is not alive, or on any error. It does no network I/O and always exits 0. Not written in `--no-tui` (no surface to approve from) or for `adapt`; `[plan_mode] approve_timeout = "0"` leaves it out entirely.
- **The exchange** (files, like signals): `.igris/plan-approval/<session uuid>.json` (0600, directory 0700), written atomically by the hook: `{"n": "<random id>", "at", "plan"}` with the plan text from `tool_input.plan` only (never `planFilePath`, which is outside the project). igris answers with `<session uuid>.decision.json`: `{"n", "behavior": "allow"|"deny"|"pane", "message"}`. A decision whose `n` doesn't match the current request is ignored. The hook builds Claude Code's output itself: allow echoes the `tool_input` it received as `updatedInput` and adds `setMode` for the resolved mode; deny passes the message; `pane` exits with no output. Both files are untrusted (a session can write them): bounded, shape-checked, keyed by the UUID igris generated. A session that forges a decision approves its own plan; that is an accepted risk, since approval from igris is a convenience for the owner, not a guard (plan mode never was one either: the session runs with the owner's rights once approved).
- **What igris shows.** The engine sees the request on its next poll, saves the plan, raises **Needs you** with reason `plan awaiting approval` (igris can now tell this one apart) and opens a plan view in the TUI: the plan (`textsafe`-cleaned, scrollable), **approve** (with the mode it will switch to), **reject with feedback** (a text field; cleaned, at most 4 KiB) and **answer in the pane** (sends `pane`, opens the session). The pane's own dialog stays usable throughout; when the owner answers there, the next poll finds the request gone with the hook and closes the view. A resumed `arise` that finds a request from a live session shows it.

**Approved by owner** (2026-10-20), for v1.1. Verified behavior:
- **`transcript_path`** is in every hook payload igris installs (`SessionStart`, `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `PermissionRequest`, `Notification`, `Stop`). It is `~/.claude/projects/<encoded cwd>/<session uuid>.jsonl`, named after the `--session-id` igris passed. `SessionStart` also carries `model` (the full id).
- **Transcript shape.** A JSONL file of records with a `type`. Usage lives on `type: "assistant"` records: `message.id`, `message.model` (e.g. `claude-sonnet-5-5`), `message.usage.input_tokens`, `output_tokens`, `cache_read_input_tokens` and `cache_creation_input_tokens`, plus top-level `requestedModel` (absent in older versions), `isSidechain` and `timestamp`. The usage of the probe's one call matched the status line's `current_usage` exactly.
- **One API response is several records.** Claude Code writes one `assistant` record per content block (`apiBlockIndex` 0, 1, 2 …), and each repeats the response's full `usage`. Records must be counted once per `message.id`; summing every record counts tokens two or three times.
- **Synthetic records.** API errors (`rate_limit`, `authentication_failed`, `server_error`) are `assistant` records with `message.model` `<synthetic>`, `isApiErrorMessage: true` and zero usage. A rejected request also carries `quotaLimits` `{status, rateLimitType: five_hour|seven_day, resetsAt, …}`, a source for v2-usage limit handling. It gives no percentage, so it can't serve as "quota left".
- **Big lines.** `api-request-blob` and attachment records can be far over 1 MiB; `assistant` records are small.
- **Subagents** write their own files, `<transcript path without .jsonl>/subagents/agent-<id>.jsonl` (next to an `agent-<id>.meta.json`), with `isSidechain: true`, the parent's `sessionId` and their own model, often not the session's (a fable subagent in an opus session, say). The main transcript holds no sidechain records.
- **Several models in one main thread** happen: three local sessions mixed opus and sonnet (an owner `/model` switch). That is exactly what the audit must catch.
- **Subscription quota.** No hook payload carries it, and the CLI has no usage command (`/usage` exists only inside the session, and scraping the pane is ruled out). The **status line** payload carries it: `rate_limits.five_hour` and `rate_limits.seven_day`, each `{used_percentage, resets_at}` (Unix seconds). Getting it involves no credentials and no API call. It is missing from the first render, before any API response, and is expected to be missing for an API-key login. The payload also has `model.id`, `context_window.used_percentage` and `cost.total_cost_usd` (igris ignores the cost).
- **A `statusLine` in igris's `--settings` file replaces the owner's status line** in that pane: the probe's pane showed the probe's line instead of the owner's.

Decided:
- **Reader** (V11-03). The `igris hook` record in `.igris/agent-state/<uuid>.json` gains `transcript` (not frozen). It is accepted only when it is absolute, clean and named `<that session's uuid>.jsonl`. igris reads it through `fsafe` (regular file, never blocking), streaming, with lines over 1 MiB skipped unparsed. Each line is decoded into a struct with only `type`, `isSidechain`, `timestamp`, `requestedModel`, `message.id`, `message.model` and the four usage counts, so no content is kept. Records with `<synthetic>` or no id are skipped, and records count once per `message.id`. An attempt counts the records whose `timestamp` falls inside it, so a `continue` (`--resume`, same file) never counts the previous attempt again. The reader keeps a byte offset and reads only what's new, every 10 s while the task runs and once when the attempt ends. Subagent files are found next to the transcript (at most 256 of them, each read the same way). Anything unreadable, missing, or of an unknown shape gives "usage unavailable" for that attempt, with one warning in the feed, and never fails a run or a task. Usage is never read for `adapt`.
- **What counts.** Per attempt: `input`, `output`, `cache_read`, `cache_write` and `messages` for the main thread, the same for subagents (`sub`), the main-thread model ids (`models`) and the subagent model ids (`sub_models`). Totals add both. Background calls Claude Code doesn't write to the transcript (session titles, say) are not counted. igris states this: the figures are "tokens recorded in the session transcripts", never billing.
- **Rank audit** (V11-04). Only the main thread is checked; subagents are counted, not audited (owner's choice). The expected model comes from the resolved `[models]` value. `fable`, `opus`, `sonnet` and `haiku` match `claude-<alias>-*`, and a `[1m]`-style suffix is ignored. A full id (`claude-…`) matches itself, with or without a `-YYYYMMDD` date suffix. Any other value (`default`, `opusplan`, a custom alias) can't be checked: the audit says `unchecked` and raises nothing. **Live** (owner's choice): the first main-thread record on another model raises **Needs you** with reason `rank_mismatch`, a `rank_mismatch` notification (urgent, in the default events) and a `rank_mismatch` run-log line. This happens at most once per attempt, and the session is never stopped or switched. The task's audit result is `ok`, `mismatch`, `unchecked` or `unavailable`.
- **Run log** (additive, v1). A new `usage` event at every attempt end (`task_done`, `task_skipped`, `task_retried`, session lost, `run_stopped` while a task runs) with `task`, `rank`, `model`, `attempt`, `session`, and new fields `usage` `{input, output, cache_read, cache_write, messages}`, `sub` (same shape, omitted when zero), `models` and `sub_models` (arrays of ids), and `audit`. `detail` gives the reason when it is `unavailable`. A new `rank_mismatch` event with `models` (the ids seen). New needs-you reason `rank_mismatch`. Never message content or the transcript path.
- **`igris usage [RUN] [--since D] [--json]`** (V11-05). It reads `runs.jsonl` only, never transcripts, and is read-only like `report`. `RUN` works as in `report` (1 is the newest, the default, or a run ID). `--since` takes a duration (`7d`, `36h`) or a date (`2026-10-01`, local midnight) and covers every run that started since then. RUN and `--since` together are a usage error (2). Text output: the runs covered; totals; tables by task (attempts, in, out, models, audit), by model and by rank; the top 5 tasks by `in + out`; the audit summary (mismatches named, red when a TTY); and the quota line. Exit codes: 1 when there are no runs, no such run, no run since D, or the log can't be read; 2 for a usage error. `--json` follows `docs/json/usage.schema.json`: `{"v":1, "runs":[…], "since", "total", "tasks":[{task, rank, model, attempts, usage, sub, models, sub_models, audit}], "models":[…], "ranks":[…], "top":[…], "audit":{ok, mismatch:[…], unchecked, unavailable}, "quota": null|{…}, "notes":[…]}`. `report` gains the per-task usage and audit (additive JSON fields, a red mark on a mismatch).
- **Run card** (V11-05). `tokens 2.3M in · 41k out` (`in` = input + cache read + cache write), updated with every read (about every 10 s), and `usage unavailable` when there is no transcript. The model id seen goes after it, red on a mismatch. The narrow layout shows `2.3M/41k`.
- **Quota: opt-in** (owner's choice; V11-06 goes ahead). `[usage] statusline = false`. When it's on, the settings file (§6.3) gets `"statusLine": {"type":"command","command":"'<igris>' hook --root '<root>' statusline"}`, which replaces the owner's status line in task panes (stated in the docs and the config comment). `hook statusline` reads at most 64 KiB, stays within the 2 s deadline and prints one line: `<ID> · <model id> · ctx 5% · 5h 4% · 7d 52%`, with the quota parts left out when absent. It saves `rate_limits` atomically to `.igris/quota.json` (`{"at", "five_hour": {"used", "resets_at"}, "seven_day": …}`, 0600, untrusted, read bounded and shape-checked), written only when the values change. The settings file is per task (`.igris/hooks/<ID>.settings.json`), so the command passes the task ID as an argument (`statusline <ID>`, single-quoted; IDs are shape-checked by the plan format). The TUI header shows `5h 4% · 7d 52%` (amber at ≥ 80%, red at ≥ 95%), with its age once it is over 10 min old. `igris usage` prints the last snapshot with its time and reset times. Without it, or with `statusline = false`: `quota unavailable`. Never from credentials, the API or the pane.
- **`[usage]`** (new): `enabled = true` (read transcripts for the counter, the run log and the audit; `false` turns all three off) and `statusline = false`.
- **SPEC §1 non-goal** "Estimating or tracking token cost … does not meter usage" becomes "Estimating, pricing or billing token cost": igris counts what its own sessions' transcripts record and never prices it. The v2-usage price estimate stays out.

That is accepted: usage is information, and the audit catches configuration slip, not a hostile session (which runs with the owner's rights anyway). - **Notifications** (V11-04). `rank_mismatch` is a new event: urgent (ntfy priority high, Gotify 8, webhook `urgent: true`), and in the default `events` of every channel, so a channel without its own list gets it. ## V12-P4 — Update check, started by the owner

**Decided by owner** (2026-10-21), for v1.2. The owner chose: no automatic or background check, because SPEC §1 promises no network calls except the notification endpoints the owner configures; instead a **Check for updates** the owner starts, which is then the only thing that contacts GitHub. After an update igris tells the owner to restart (no re-exec). It ships in 1.2. The ROADMAP non-goal "Auto-update / self-upgrade" stands: igris never updates on its own and never replaces its own binary; it hands over to the package manager that installed it.

Decided:
- **Trigger.** Only the owner's action: home's **Check for updates** (a key free on home, listed in help) and `igris update [--check]`. Never at start, on a timer, in the run view or in a `--no-tui` run. No config keys: there is nothing to switch on.
- **Request.** `GET https://api.github.com/repos/drilonrecica/igris/releases/latest` with `Accept: application/vnd.github+json` and `User-Agent: igris/<version>`, 10 s timeout, body at most 1 MiB, proxies from the environment. Only `tag_name` is read and must match `^v\d+\.\d+\.\d+$` (that endpoint skips pre-releases). The release URL is built by igris (`https://github.com/drilonrecica/igris/releases/tag/vX.Y.Z`); no other response text is shown or used.
- **Compare** with the running version (ldflags, else the build info's module version). A development or pseudo-version build says it is a development build and names the latest release, offering no update; an equal or newer version says igris is up to date.
- **Install method**, from `os.Executable` with symlinks resolved and the build info:
  - **brew** — the path contains `/Cellar/igris/`: argv `brew upgrade igris`.
  - **go install** — no ldflags version and a release module version in the build info: argv `go install github.com/drilonrecica/igris/cmd/igris@vX.Y.Z` with `GOBIN` set to the running binary's directory, so the same file is replaced. When it fails with `unknown revision` in its output, igris adds the hint to retry with `GOPROXY=direct GONOSUMDB=github.com/drilonrecica/igris` (the checksum database lags a new tag for about 30 minutes).
  - **archive or unknown** — no command: the release link and the download, verify (`ssh-keygen -Y verify` against `allowed_signers`) and install steps of the release notes.
- **Update on home.** A newer version opens a dialog: current → latest, the method, the exact command, **Update** · **Not now**. While a run holds this project's lock (or home is read-only), Update is not offered ("update after the run ends"). The dialog notes that runs in other projects keep going and their sessions then run the new igris for `igris done`. The command runs through the command runner, as argv, 10 min timeout, with igris's environment minus the notification-secret variables (as git, §6.5); its output tail is cleaned (`textsafe`). On success igris runs `<igris in PATH> version` and says `Updated: igris in PATH is now X.Y.Z. Quit and start igris again.`; on failure it shows the output tail (and the hint).
- **`igris update`.** `--check` prints the current and latest versions and the method, and runs nothing. Without it: the command, then `Update? [y/N]` on a terminal; `--yes` skips the question; without a terminal and without `--yes` it exits 1 saying to pass `--yes`. Archive installs print the steps. Exit 0 on success (also when up to date), 1 on a network or command failure, 2 on a usage error. A new command, additive under §19, frozen once shipped.
- **SPEC.** §1 becomes "Igris makes no network calls except to the notification endpoints the user configures, and to GitHub's releases API when the owner checks for updates (§14)"; §14 `igris update`; §15.6 the home action and dialog; §16 safety; §19 the new command.
- **Threat model.** The response is untrusted: bounded, only a shape-checked tag used, no text shown. The command is built from that version only, as argv, never through a shell. The integrity of the new binary stays with brew (the formula's sha256) and Go (the checksum database); a forged response can at worst name a version the package manager then refuses or resolves.

  - **linear**: Linear's CSV export (header with `ID`, `Title`, `Description`, `Status`, …);
  - **jira**: Jira's CSV export (header with `Issue key`, `Summary`, `Description`, `Status`, …; repeated `Labels` and link columns joined).
  
  It writes at most 1000 items (more: an error naming the limit) to `.igris/draft/import.json` (`{"v":1,"source","items":[{"key","title","body","state","labels","links"}]}`, text cleaned of escape sequences and control characters, each body cut at 16 KiB, saying so), which the session reads. Done or closed items become `done` rows; deps come from the export's blocking links where it has them, else the session proposes them. igris never contacts GitHub, Linear or Jira, and never writes back. The parsers have fixtures (synthetic, never a real export) and a fuzz target.
- **Extend** (owner's choice: a fragment igris splices in). The plan must be valid (`draft extend` on an invalid plan points to adapt). The session writes `.igris/draft/<plan-name>.extend.md`: `##` phase sections with task tables. A section whose phase ID exists adds rows to that phase; any other section is a new phase. igris checks the fragment (every new ID unique across the plan, no Status but `ready`/`blocked`, no column the phase's table lacks — rows are written in the existing table's column order, missing cells empty — and deps naming existing or new IDs), builds the extended plan in memory, validates it, and shows the review, which lists only additions, each with its file. On Accept: each changed file is backed up to `.igris/draft/<file-name>.<timestamp>.bak.md` (UTC, `20060102-150405`), then rows are inserted after the last row of their phase's table and new phases appended at the end of the main plan file (after one blank line), atomically, keeping the file mode; if any file changed on disk since it was read, nothing is written. Every existing byte stays: the writer's byte-preservation tests cover each insert. On a **split plan** (owner's choice: supported) new rows go into the file their phase lives in, new phases into the main file. This is the third way igris writes outside Status cells, after adapt and `init`, and only after the owner's Accept (§4 rule 6 amended).
- **Home** (owner's choice). `D` **Draft…**: a picker of **From a goal**, **From a spec file…**, **Import an export…**, **Extend the plan…** (a text field for the path or the request), then the draft's progress, Open session, then the review as for adapt. Goal, spec and import are offered when `igris.toml` is valid (or missing) and the plan file is missing; Extend when the plan is valid; none while a run holds the project (read-only home) or the backend is unreachable. The GET STARTED plan step offers **Draft…** next to **Plan from template…**.
- **Exit codes.** 0 when the proposal is accepted or rejected, or the owner stops waiting (the session stays open); 1 when a plan is in the way (goal, spec, import), the plan is invalid (extend), the input can't be read or parsed, the session is lost or skipped, the backend or project can't be used, or the review fails; 2 for usage errors.
- **Frozen in 1.x** (§19): the `draft` subcommands, flags and exit codes; `[draft] model`; the path `.igris/draft/`. Not frozen: the prompt, the rules, `import.json`'s contents, the proposal's wording.
- **Threat model.** New boundary: the spec and the export are untrusted input to a session. The session runs in `manual`, writes only a proposal, and nothing reaches the plan without the owner's Accept after the review; import text is cleaned before the session or the TUI sees it, and the parsers are bounded and fuzzed. Accepted risk: a malicious spec or issue can steer what the session proposes; the review is the guard.
- **Who builds what.** V13-01: the pipeline (`draft` command and its subcommand dispatch, `[draft] model`, the rules, `igris done DRAFT`, `.igris/draft/`, the shared session, validate and review path, the empty-slot rule, the second confirmation). V13-02: goal (prompt, interview, e2e with the fake backend). V13-03: spec (path checks, prompt). V13-04: import (three parsers, detection, `import.json`, fixtures, fuzz target). V13-05: extend (fragment parser and checks, the splicer per file with byte-preservation tests, split plans). V13-07: home's `D`. V13-06: README, the site's drafting page, CHANGELOG, release notes, threat model, SPEC/help consistency.

## V2C-P1, V14-P1 — v2 as a 1.x train; serve and attach

**Approved by owner** (2026-10-21). Each choice was the agent's recommendation. SPEC is amended when V14 starts (V14-01), after v1.3.0 ships, so the V13 run never sees a half-specified 1.4.

**The train (V2C-P1).**
- **No breaking 2.0.** The v2 abilities (ROADMAP v2.0) ship as additive 1.x releases under §19, following plan format 2: a newer format or state version that an older igris refuses cleanly, never misreads, is additive. No `igris migrate`, no 1.x maintenance window. A 2.0 happens only if something truly must break; nothing found so far does. The v2-core rows (V2C-01…05) are replaced by V14; the v2-rel rows (V2X) are dropped.
- **Order:** 1.4 serve/attach → 1.5 parallel execution (V2P rows, renumbered V15, V2P-P1 its decision) → 1.6 remote control (V2R rows, renumbered V16). Parallel first: the bigger win for the owner's use, its prerequisites shipped in 1.1 (usage, rank audit, parallelism report), and the web UI is then designed for N sessions from the start; remote is security-heavy and wants a stable multi-task model. The v2-usage leftovers (limit handling, budgets, price estimate) are a later 1.x when wanted.
- **State v4 comes with parallel (1.5),** an `active` list next to `current`. 1.4 changes no file format (a client's event cursor lives in the client), so 1.3 can still resume a run 1.4 left.

**Serve and attach (V14-P1).**
- **Every run is attachable,** through a unix socket. `igris arise` (and home's Arise) becomes serve + attach: it starts the engine in a background `igris serve` process (`setsid`, stdout and stderr to `.igris/serve.log`, 0600, cut at 16 MiB) and attaches to it, so every run has one engine host. `arise --no-tui` stays in-process: scripts expect it to end with the run.
- **`igris serve [PHASE]`** takes arise's run flags (`--through`, `--mode`, `--worktree`, `--only`/`--from`/`--until`, `--force-unlock`), runs the engine headless in the foreground with `--no-tui`'s plain lines on stdout, and ends with the run or on a stop. It holds `igris.lock` (its pid) and owns SIGHUP, SIGINT and SIGTERM (stop as today). `serve --mode yolo` asks the typed phrase on a terminal and refuses without one (exit 1): no flag around §7.3. arise asks the phrase in its TUI and passes the confirmation in the socket handshake.
- **Headless panes:** outside herdr and tmux, `serve` with the tmux backend starts a detached tmux session `igris-<project>` (`tmux attach -t igris-<project>` to look); herdr needs its server reachable.
- **`igris attach`** opens the run view of this project's live run. **`q` asks Detach / Stop run / Cancel, Detach focused** (owner's choice): Detach leaves the run going, Stop run stops it as `x` (sessions stay open). A closed terminal or a dropped ssh connection detaches. An attached client may do everything the TUI can, skip-permissions included after the typed phrase in that client (owner's choice): it is a terminal, and only the owner's user reaches the socket. Remote (HTTP, 1.6) gets narrower rules, never yolo.
- **`igris stop`** (owner's choice): asks the live run over the socket to stop (sessions stay open), waits until it has, exit 0; exit 1 when no run is live here. For scripts and cron.
- **Home** (owner's choice): bare `igris` with a live run on this host opens home as today, with the run shown and **Attach** as the first action (enter or `t`; `o` stays Open session). Home's Arise spawns serve and pushes the attached run view.
- **Socket.** `.igris/igris.sock`, 0600, in the 0700 `.igris/`; removed at exit, a stale one (no listener) replaced. When the path is too long for a unix socket (~104 bytes on macOS, 108 on Linux), it lives at `$XDG_RUNTIME_DIR/igris/<first 16 hex of sha256(root)>.sock`, else in a 0700 `igris-<uid>` directory under `os.TempDir()`, and `.igris/igris.sock.path` names it. On Linux the server checks the peer's uid (`SO_PEERCRED`, stdlib `syscall`); elsewhere the file mode and the directory are the guard.
- **Protocol 1.** Newline-delimited JSON, at most 1 MiB per line. The client sends `hello` (`{"v":1,"type":"hello","client":"igris 1.4.0"}`); the server answers `snapshot` (what the run view needs: run, phases and tasks with status, the current task, a pending question or plan approval, mode, pause, the last feed lines, tokens and quota), then events. **Events use the run log's v1 envelope and field meanings** (owner's choice: `v`, `at`, `type`, `run`, `task`, `rank`, `model`, `detail`, …) plus socket-only types and fields for what the log never holds (cells written, waiting lists, session refs, `verify_started`, pause and mode changes, question payloads, hook output, live tokens, quota, plan text); clients ignore what they don't know. Commands mirror `engine.Command` one to one (`pause`, `stop`, `done`, `skip`, `retry`, `answer`, `mode`, `task_mode`, `plan`), each with an `id`, answered `ack` or `error`; the tail is a request (`tail`, `n`). A slow client is dropped (bounded buffer), never blocks the engine, and gets a fresh snapshot when it reattaches. The first answer to a question wins; every client sees it as an event.
- **Versions** (owner's choice): protocol 1 covers all of 1.x, additive like `--json`. A client attached to a serve of another igris version (after `igris update` during a run) works, and its header says `served by igris 1.4.0`, with a note that the run keeps that igris until it ends.
- **Engine:** unchanged inside. serve hosts `engine.Engine`; its `Events` fan out to the run log and notifier (as now) and to the clients; `Send` takes their commands. The run view gets a client-side engine adapter, so it renders an in-process engine or a remote one. Signals, `igris done`, the plan writer and notifications all live in serve, unchanged.
- **Threat model.** New boundary: the socket. Same user only (file mode, directory, peer uid on Linux); every message bounded and shape-checked; commands pass the same engine checks as the TUI's (an agent task's skip still asks; yolo still needs the phrase). Accepted risk: any process of the owner's user can drive a run, as it can already edit the plan or `igris.toml`.
- **Frozen (§19):** `serve`, `attach`, `stop`, their flags and exit codes; socket protocol 1 (message types, the run-log envelope); the paths `.igris/igris.sock` and `.igris/igris.sock.path`. Not frozen: `serve.log`'s contents; snapshot fields beyond the documented ones.
- **Who builds what:** V14-01 the SPEC amendments and `internal/serve`; V14-02 `serve` and `stop`; V14-03 the client and `attach`; V14-04 arise and home as serve + attach; V14-05 the docs; V14-G the gate.

## V15-P1 — Parallel execution (v1.5)

**Approved by owner** (2026-10-21), for v1.5, the second release of the 1.x train (V2C-P1). Each choice was the agent's recommendation; ROADMAP's v2-par design notes are the background. SPEC is amended when V15 starts (V15-01), after v1.4.0 ships.

- **Opt-in per phase** (owner's choice). `<!-- igris:parallel -->` on a line of its own under a phase heading, in a plan declaring `<!-- igris:format 3 -->` (format 2 plus the marker and the `Group` column below; igris 1.0–1.4 refuse it), means "the deps in this phase are complete". A marked phase runs up to `[parallel] max` tasks at once (new table; default 2, 1–8) or `arise`/`serve --parallel N`; `[parallel.ranks]` caps per rank (default `fable = 1`, others uncapped up to `max`). Unmarked phases stay sequential, so every 1.x plan keeps its meaning. `check` warns when a marked phase has tasks with no deps that the file order seems to imply (a task naming an earlier one's ID in its text).
- **Scheduling.** Among the marked phase's tasks, every task that isn't satisfied or active and whose deps are all satisfied is a candidate, in file order: §5.1 applied up to `max` times, within the rank caps. **`Group`** (owner's choice), an optional column: tasks with the same non-empty value never run at the same time. **Owner tasks run alone** (owner's choice): a `user` or `agent + user` task (gates included) starts only when nothing else runs, and nothing starts beside it (`[parallel] exclusive_owner_tasks = true`, default).
- **Isolation.** Every task of a parallel phase runs in its own git worktree, `.igris/worktrees/<run>/<task>` on branch `igris/<run>/<task>`, from the run branch's current head (v0.6's worktree mode), with its own session and verify. `IGRIS_SLOT=0..max-1` (owner's choice) is set in its session, verify and task hooks so a project can offset ports or test databases; `[parallel] serial_verify = true` runs verify one at a time while sessions stay parallel (default false). A worktree's copy of the plan is never written: Status lives only in the main plan.
- **Integration in completion order, rebased** (owner's choice). When a task passes verify, igris commits in its worktree (one commit, as today; `commit = "ask"` asks then), rebases it onto the run branch and fast-forwards, then runs verify on the integrated tree. Status `done` is written only after that, so dependents never start on code that isn't in the run branch. Linear history, one commit per task.
- **When a task doesn't integrate** (owner's choice: rerun once, then ask): a rebase conflict or a verify failure after the rebase discards the task's branch and reruns the task fresh on the new base, once (`[parallel] on_conflict = "rerun"`, default; `"ask"` goes straight to Needs you). A second failure is Needs you with the conflict list or the verify output. The resolver session (ROADMAP: `review`, `auto`) is a later 1.x, opt-in.
- **Overlap watcher** (owner's choice: flag). Every poll igris runs `git status --porcelain` in each active worktree and warns once per file two active tasks both change (`V15-03 and V15-04 both change internal/tui/home.go`), in the feed and the run log. Nothing is held.
- **State v4.** `state.json` gets an `active` list (task, attempt, session ref, worktree, slot) next to `current` (kept, the first active task, so 1.4-era readers of `--json` keep working); version 4, migrated in memory from 1–3, refused by igris 1.0–1.4 like every newer version. Resume reattaches every active task.
- **UI and notifications.** The run view shows one card per active task when wide, a switcher when narrow; one Needs-you queue in plan order; notifications aggregated (`2 tasks need you`). The socket's events carry `task` as today; the snapshot lists every active task.
- **Unchanged:** a session never sees another task; skip-permissions is still the per-run typed phrase; igris never picks a model; `--no-tui` runs parallel phases too.
- **Frozen (§19):** plan format 3 (the marker, `Group`), `[parallel]` and `[parallel.ranks]`, `--parallel`, `IGRIS_SLOT`, state v4, the new run-log events (`integrated`, `integration_failed`, `overlap`). Not frozen: the worktree paths' contents, the card layout.

## V15-01 — Parallel execution: decided while implementing

**Owner's delegation** (2026-10-22: "you decide what makes most sense"). V15-P1 named a task's worktree `.igris/worktrees/<run>/<task>` on branch `igris/<run>/<task>`. In worktree mode (§6.8) the run already has `.igris/worktrees/<run-id>` on `igris/<run-id>`: git refuses a branch under an existing branch name (a ref can't be both a branch and a directory of branches), and a task worktree inside the run's worktree shows there as untracked, so the run's clean check at its end never passes. Decided: one naming in every run, `.igris/worktrees/<run-id>-<ID>` on `igris/<run-id>-<ID>`, which clashes with neither. V15-P1 didn't freeze the worktree paths; SPEC §6.2, §6.11 and §13 say this.

## V16-P1 — Remote control (v1.6)

**Approved by owner** (2026-10-21), for v1.6, the third release of the 1.x train. Each choice was the agent's recommendation; ROADMAP's v2-remote notes and invariants hold (off by default, never yolo remotely, no relay or igris cloud). SPEC is amended when V16 starts (V16-01).

- **Listener** (owner's choice). Off unless `[serve] http = "ADDR:PORT"` (or `serve --http`) is set; it runs next to the socket in the serve process, speaking protocol 1 over HTTP (commands as POST, events as server-sent events). Loopback (`ssh -L`) and Tailscale addresses (100.64.0.0/10, fd7a:115c:a1e0::/48; WireGuard-encrypted) bind directly; any other address needs `--listen-public` plus `[serve] tls_cert` and `tls_key` (igris serves TLS from them; no ACME), and igris warns at start.
- **Auth** (owner's choice). `igris serve token [--rotate]` creates a random 32-byte token per project (`.igris/serve-token`, 0600) and prints a pairing URL plus a QR code once. Opening the URL sets an `HttpOnly`, `Secure` (on TLS), `SameSite=Strict` cookie and redirects to a URL without the token. Every request needs the cookie or `Authorization: Bearer`; every action carries a CSRF token; failed auth is rate-limited per address; strict security headers (CSP without inline script, `frame-ancestors 'none'`, no referrer). The QR code is drawn by a small hand-rolled encoder (byte mode, error correction M, versions 1–10) in the standard library only, as the LCS diff was (P0-01): no new dependency.
- **Web UI** (owner's choice: the narrow TUI's actions). Embedded (`embed`, `html/template`, one small static script file for the event stream, no build step), phone-first: run state, phases and tasks, every active task with its tail, answer questions, approve or reject plans (feedback required on reject), pause, stop, retry, done, skip, the mode for the next sessions **except skip-permissions** (never offered or accepted remotely). Skip, stop and done ask a second confirmation. Starting a run stays in the terminal.
- **Answer from ntfy** (owner's choice: in 1.6). With the listener on and `[notify.ntfy] actions = true`, a pending question's ntfy message gets action buttons (`Commit`/`Don't commit`, `Skip`/`Keep`, `Retry`/`Stop`, `Approve`/`Open`) whose URLs carry a single-use, 10-minute, question-bound token (never the owner token), stored hashed in serve's memory: a leaked notification answers that one question, once, until it expires or the question is answered. Plan rejection needs feedback, so it opens the web UI instead. Discord, Slack and the others can't receive replies: unchanged.
- **Threat model.** New boundary: remote callers are untrusted until authenticated. Security review V16-05 covers auth, tokens, CSRF, headers, listener exposure, replay and yolo never remote.
- **Frozen (§19):** `[serve] http`, `tls_cert`, `tls_key`, `serve --http`, `--listen-public`, `igris serve token`, `[notify.ntfy] actions`, the HTTP mapping of protocol 1. Not frozen: the web UI.
